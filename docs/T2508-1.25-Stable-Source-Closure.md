## Scoped live acceptance

Persistent Kitty ATLAS acceptance is **deferred and unaccepted**, because of the
confirmed Kitty 0.32.2 missing chunked animation-upload ACK. The standalone evidence
does not establish newer-Kitty or clean-config behavior. Frame/control ACK
assumptions and ordinary FRAME flicker remain unresolved.

The maintainer's DCurses WSL2 observations accept immediate input, text output and
correct ordinary FRAME input/display with flicker. Earlier alpha.2 Windows
Terminal/Contour observations accept FRAME movement, help restoration, resize
recovery and exit, with a transient Contour resize strip. They do not qualify the
persistent path or guarantee flicker-free/atomic rendering.

The instruction to complete 1.25 authorizes release preparation with these
limitations; it supersedes older follow-ups requiring more Kitty testing before
stable preparation. It does not mark those tests passed. No backend replay,
persistent Sixel emulation or identifier workaround is introduced.

## Qualification authority

The hold-only source `c0f3061b4c18ba751fc056aee96ba4199af68420` passed all nine
Staging runtime/package jobs in
[run 2135](https://github.com/uniblab/Icod.Terminal/actions/runs/37229124683).
That is baseline evidence, not proof for the subsequent stable-version source.

The stable-version source must pass all nine jobs at one exact head:

1. Runtime Windows, Linux and macOS, on .NET 8/9/10.
2. Package build and equal frozen API snapshots.
3. Foundation, Presentation, Semantic/hardening and Stable 1.x package consumers.
4. Validated package artifact with package and symbols.

The final PR description records the exact stable source SHA, run, job conclusions,
test counts, API fingerprint and package/symbol hashes from the validated artifact.
This external evidence avoids changing the qualified source merely to insert its
own commit hash. Any later source/documentation change requires the matrix again.

## Publication sequence

After successful source qualification, maintainer integration and the mainline
Release workflow remain required. Only after mainline validation succeeds may
`v1.25.0` trigger the existing tag-release workflow, which revalidates runtime and
packages before NuGet/GitHub publication. This preparation does not claim that
1.25.0 has already been published. Stable package README metadata is intentionally
aligned with the version enforced by the existing package gate.

The final publication must carry the known graphics limits unchanged. Further
graphics work requires a new maintainer scope decision and a properly testable
Kitty environment.
