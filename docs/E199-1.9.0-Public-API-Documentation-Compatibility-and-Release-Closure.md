## Final documentation and sample audit

A final consumer-facing review after the first complete E199 candidate identified one compatibility-teaching gap in the samples rather than a runtime/API defect.

The 1.9 release intentionally adds `TerminalEventKind.Semantic`. The permanent compatibility policy therefore warns consumers with exhaustive event-kind switches to handle additive values when adopting later minor releases. Two event-oriented samples still demonstrated the pre-1.9 exhaustive-switch pattern and would have thrown if they received a valid `Semantic` event.

The final polish pass therefore:

- updates `Icod.Terminal.RichInput.Sample` to format semantic notification events, including identifier and one-based button number when present;
- updates `Icod.Terminal.Query.Sample` to demonstrate that typed queries, ordinary input, lifecycle events, and semantic events coexist on the same authoritative reader;
- gives both samples a nonfatal outer-event fallback so a newer compatible 1.x event kind does not automatically crash the sample loop;
- keeps payload-presence checks strict for event kinds the sample does understand;
- corrects `Icod.Terminal.Color.Sample` wording from "input event" to the broader "terminal event" contract;
- adds a complete safe event-loop recipe plus forward-compatibility guidance to `docs/Input-and-Events.md`;
- sharpens `samples/README.md` so semantic-event discovery is visible in the at-a-glance table and RichInput/Query descriptions.

A repository regression test, `SampleSemanticEventCompatibilityTests`, was committed first at `df65bbc59107b333e4e6d86952e91440689749b7`. Pull-request workflow `#1461` / `34531480255` provided the required RED evidence on Linux: the solution built with zero warnings and zero errors, the existing 1,788 tests passed on each TFM, and exactly three new assertions failed because RichInput and Query lacked `TerminalEventKind.Semantic` handling and Color retained stale input-only wording.

The sample/documentation changes are intentionally outside the public/runtime API surface. They require a new exact-head Staging qualification because sample sources and permanent documentation are part of the release candidate.

## Permanent behavioral contract frozen by E199

### One authoritative reader

No 1.9 feature opens a second terminal input reader. Ordinary input, semantic observations, and active query responses continue through the same session-owned input coordinator/router.

### Query precedence

A frame owned by an active or bounded late-response query transaction is never also delivered as a semantic notification event.

After malformed/oversized semantic recovery, the decoder restarts at query precedence before later buffered traffic is considered.

### Bounded semantic ownership

Recognition of an unsolicited report grants bounded ownership rather than trust. Malformed/oversized owned reports are consumed/recovered without leaking hostile bytes into ordinary application text.

Semantic events use the same bounded application-event ordering/backpressure domain as ordinary input; there is no unbounded semantic side queue.

### Notification interaction semantics

Interactive reporting is explicit opt-in and requires a caller-supplied identifier. Button labels are bounded before commitment and encoded with the protocol-defined U+2028 separation semantics.

The public event model distinguishes `Closed` from `CloseTrackingUnavailable` and preserves one-based button numbering.

### Lifecycle

Notification requests and reports are application output/observations, not reversible session state. The library does not retain a hidden notification database, replay sent notifications after resume, synthesize interaction reports, or automatically close identified notifications on disposal.

### Trust boundary

Notification identifiers and interaction reports are validated but unauthenticated terminal-controlled data. They are correlation information, not authorization tokens or proof of a trusted desktop/user action.

## Maintainer handoff rule

After E199 exact-head qualification:

1. the PR may be marked ready for maintainer review/merge;
2. the maintainer performs the merge;
3. the exact resulting `main` commit must pass the repository's Release distribution validation;
4. the maintainer creates/pushes `v1.9.0` only after that Release validation succeeds;
5. publication uses the curated `docs/releases/1.9.0.md` notes.

A green PR is therefore release-candidate evidence, not merge/tag/publication authorization for automation or this development tranche.
