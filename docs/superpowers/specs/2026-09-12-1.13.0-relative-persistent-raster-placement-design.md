# Icod.Terminal 1.13.0 Relative Persistent-Raster Placement Ownership Design

**Release:** `1.13.0`  
**Theme:** relative persistent-raster placement ownership  
**Base:** published `Icod.Terminal 1.12.0`  
**Stable compatibility floor:** `1.0.0`

## Goal

Add one bounded persistent-placement positioning/lifetime mode: a placement may be created relative to another current placement while preserving the existing opaque resource/placement identity model, one authoritative query path, generation-scoped ownership, and deterministic cleanup.

The feature is intentionally modeled as local ownership topology plus reviewed backend encoding. It is not exposed as a generic scene graph and does not make terminal protocol identities public.

## Existing foundation

Version 1.11 established:

- opaque terminal-resident raster resources;
- opaque persistent placements;
- acknowledged create/update transactions;
- generation-scoped placement/resource certainty;
- child-before-resource cleanup;
- bounded registries;
- current-cursor placement.

Version 1.12 added:

- bounded source-pixel rectangles;
- signed z-order;
- resource-aware rectangle validation;
- exact preservation of legacy placement bytes when advanced options are omitted.

Version 1.13 must preserve all of those contracts when relative-placement APIs are unused.

## Architectural decision: immutable parentage

A relative placement chooses its parent at creation and that parent never changes.

There is no reparent API and no mutable parent property.

This decision is deliberate because it:

- prevents graph cycles through the public API by construction;
- makes relative depth stable for a placement lifetime;
- allows parent-subtree cleanup to be reasoned about locally;
- prevents update semantics from changing ownership topology;
- reduces acknowledged update state to offsets plus common placement geometry;
- creates a stable base for possible future virtual/Unicode-placeholder anchoring without coupling 1.13 to that feature.

A later release may review reparenting separately, but 1.13 makes no compatibility promise for it.

## Two independent ownership relationships

Persistent placement ownership has two distinct axes.

### Resource membership

Every placement belongs to one `TerminalRasterResource` and consumes one private placement identity for that resource/session generation.

### Relative lifetime parentage

A relative placement additionally has one immutable parent placement.

The parent and child may place different raster resources:

```text
Resource A
    -> Placement A1
          |
          +-- relative lifetime parent of Placement B1

Resource B
    -> Placement B1
```

Disposing Placement A1 must remove Placement B1 and B1 descendants, but Resource B remains independently owned unless it is separately disposed or invalidated.

The registry must therefore not equate placement-parent ownership with resource ownership.

## Relative depth

Ordinary current-cursor placements have relative depth 0.

A relative placement has:

```text
RelativeDepth = Parent.RelativeDepth + 1
```

The public portable ceiling is 8.

Creation producing depth 9 is rejected locally before reservation/output. This gives a deterministic cross-terminal contract rather than relying on a backend-specific larger private limit.

## Cycle model

Public cycle construction is impossible under these rules:

1. a new placement may reference only an already-existing current parent;
2. the new placement has no descendants before it is published;
3. parentage never changes.

The registry should still validate ancestry defensively when reserving a relative placement. Any inconsistent internal graph state fails closed before protocol output.

The backend `ECYCLE` status remains parsed/handled defensively because terminal responses are untrusted, but a correctly functioning local API should never intentionally emit a cyclic request.

## Offset semantics

Relative placement uses two signed terminal-cell offsets:

```text
columnOffset
rowOffset
```

They are measured in terminal cells relative to the parent placement.

They are not:

- source-image pixels;
- terminal screen coordinates;
- pixel-within-cell offsets;
- DCurses layout coordinates owned by a virtual screen.

The initial contract accepts the full signed CLR `int` domain unless protocol qualification demonstrates a narrower portable requirement.

## Common geometry remains shared

The existing `TerminalRasterPlacementOptions` continues to own common placement geometry:

```csharp
public sealed class TerminalRasterPlacementOptions {
    public int? Columns { get; set; }
    public int? Rows { get; set; }
    public TerminalRasterSourceRectangle? SourceRectangle { get; set; }
    public int? ZIndex { get; set; }
}
```

1.13 deliberately does not duplicate those properties in a second relative-options type.

This keeps one validation implementation and one compatibility contract for crop/extents/z-order.

## Public API

The intended additive API is:

```csharp
public ValueTask<TerminalControlResult<TerminalRasterPlacement>>
    TerminalRasterResource.CreateRelativePlacementAsync(
        TerminalRasterPlacement parent,
        int columnOffset,
        int rowOffset,
        TerminalRasterPlacementOptions? options = null,
        CancellationToken cancellationToken = default
    );

public ValueTask<TerminalControlMutationResult>
    TerminalRasterPlacement.UpdateRelativeAsync(
        int columnOffset,
        int rowOffset,
        TerminalRasterPlacementOptions? options = null,
        CancellationToken cancellationToken = default
    );
```

The T130 regret gate may refine naming before T132 API freeze, but not the approved semantic shape.

### Creation semantics

`CreatePlacementAsync(...)` remains current-cursor placement.

`CreateRelativePlacementAsync(...)`:

- requires a non-null parent handle;
- requires the parent to belong to the same live `TerminalSession`;
- requires parent and child resource to be current in the same generation;
- rejects depth greater than 8;
- reserves a new child placement identity only after local validation;
- preserves parent identity privately;
- emits no cursor movement;
- returns the same public `TerminalRasterPlacement` abstraction as ordinary placement.

### Update semantics

`TerminalRasterPlacement.UpdateAsync(...)` remains available for all placements.

For an ordinary placement it retains the existing current-cursor replacement contract.

For a relative placement it preserves:

- the immutable parent;
- current relative column offset;
- current relative row offset;

while replacing common crop/extents/z-order options.

`UpdateRelativeAsync(...)` is valid only for relative placements and replaces:

- column offset;
- row offset;
- common placement options;

while preserving the parent.

Calling `UpdateRelativeAsync(...)` on an ordinary placement is a local programming error and must fail before output.

## Internal placement state

`TerminalPersistentRasterPlacementState` gains immutable/controlled relationship state:

```text
Parent          nullable placement state, immutable
RelativeDepth   integer, immutable
ColumnOffset    signed int, mutable only after successful relative update
RowOffset       signed int, mutable only after successful relative update
```

Offsets must not be changed locally before terminal acknowledgement succeeds.

The state object therefore needs synchronized or atomic update semantics sufficient to prevent a failed acknowledged update from changing the locally retained offset state.

## Registry graph

`TerminalPersistentRasterRegistry` continues to retain:

- resources;
- global placements;
- resource -> placements membership;
- private image numbers;
- private placement ids;
- generation.

It additionally maintains parent -> relative-children membership.

Operations that remove a placement must update both membership dimensions exactly once.

### Currentness

A relative placement is current only when:

- its own placement state is current;
- its resource is current;
- its parent is current;
- every required ancestor relation remains present in the same registry generation.

Because parentage is immutable and depth is bounded, this ancestry check is bounded by at most 8 parent links.

## Cascading lifetime

### Parent placement disposal

Disposing a parent placement releases its full relative descendant subtree.

Terminal cleanup is emitted deepest-first while identities remain current. This avoids sending a child delete after a parent delete that may already have cascaded terminal-side removal.

The parent is deleted last.

### Resource disposal

Disposing Resource A releases every placement directly belonging to Resource A.

If one of those placements is a parent of descendants belonging to Resources B/C/etc., those descendant placements are also released because their parent lifetime ended.

Resources B/C remain owned.

Terminal placement deletes are emitted deepest-first, then Resource A data is deleted.

### Session teardown

Current placements are drained deepest-first before resources.

Stale generation cleanup remains local-only.

### Idempotence

A placement may be reached by both resource-membership cleanup and parent-subtree cleanup. The registry must release it once, return deterministic released sets, and never double-free private placement ids.

## Backend encoding

The reviewed Kitty relative-placement form extends the existing persistent placement command with private parent and offset fields corresponding to:

```text
P  parent terminal image id
Q  parent placement id
H  signed horizontal/column cell offset
V  signed vertical/row cell offset
```

The child still uses its own private:

```text
i  child image id
p  child placement id
```

and retains `C=1` no-cursor-movement behavior.

Common 1.12 geometry remains encoded in deterministic order after relationship fields according to the reviewed encoder contract.

Current-cursor placement bytes must remain exactly unchanged when parent/offset semantics are absent.

No protocol field names or numeric identities appear in public API.

## Acknowledged create/update transaction

Relative create/update reuses the same authoritative input/query transaction manager as existing persistent placement operations.

Response correlation remains on the child image id + child placement id.

Wrong parent/child identities do not satisfy another transaction.

A successful relative update commits new local offsets only after a well-formed correlated success response.

If the acknowledgement fails, local offsets remain the last successfully acknowledged values.

## Terminal error semantics

### `ENOPARENT`

This means terminal-side certainty for the parent placement relationship is lost.

Expected local response:

- return controlled `Unavailable` for the operation;
- invalidate the parent placement subtree locally;
- do not automatically invalidate the parent raster resource merely because one placement is missing;
- do not replay/recreate hidden state.

### `ECYCLE`

Return controlled failure. The local API should make this unreachable under correct state, so occurrence is backend/protocol evidence rather than a reason to mutate the public graph contract.

### `ETOODEEP`

Return controlled failure. Local depth 8 should make this unreachable on a conforming reviewed backend.

### `ENOENT`

Retain the existing missing-image/resource invalidation semantics where the terminal indicates the referenced raster resource no longer exists.

### Malformed/wrong/late responses

Retain existing bounded parsing, identity ownership, timeout, and late-response rules.

## Generation invalidation

`InvalidateState()` and lifecycle generation changes stale the complete graph.

No stale parent/child numeric identity is emitted after invalidation.

Subsequent placement disposal is local-only.

Resources remain governed by existing generation-scoped semantics.

## Capacity bounds

Existing local ceilings remain unchanged:

```text
maximum live persistent resources   256
maximum live persistent placements 4096
```

Relative parent/child edges are bounded by live placement count and maximum depth. No unbounded graph structure is introduced.

## Capability model

No new `TerminalCapability` value is added.

`PersistentRasterGraphics` remains the coarse verified runtime capability for persistent placement operations, including the reviewed relative-placement subset.

If later evidence shows that relative placement support needs a separately observable semantic capability, that is a future compatibility decision rather than assumed in 1.13.

## Security and privacy

Relative placement adds caller-supplied cell offsets and local ownership relationships only.

It does not expose:

- terminal numeric identities;
- terminal text contents;
- files/shared memory;
- hidden raster copies;
- terminal screen coordinates;
- additional process/PTY state.

All acknowledgements remain untrusted external input. Correlation establishes routing ownership, not terminal authenticity.

## `Icod.DCurses` boundary

1.13 does not add a DCurses raster layout layer.

DCurses continues to own cells/windows/layout/damage/virtual-screen policy. The relative-placement API is a lower-level terminal-resident ownership primitive that a future higher-level consumer may choose to use.

No downstream source change is required merely because Terminal 1.13 adds this API.

## Explicit exclusions

Version 1.13 does not include:

- mutable parentage or reparenting;
- Unicode placeholder / virtual placements;
- animation/frame lifecycle;
- absolute screen-coordinate placement;
- pixel-within-cell offsets;
- scene/window/cell/layout ownership;
- caller-selected raster backend;
- public Kitty ids;
- generic raw Kitty command dispatch;
- automatic replay/re-upload;
- retained source-image cache;
- image-file decoding/transcoding;
- Sixel persistent-resource emulation;
- PTY/ConPTY process hosting.

## Compatibility

1.13 is additive over the stable `1.0.0` floor and published 1.12 surface.

When relative APIs are unused, 1.12 behavior remains unchanged:

- current-cursor placement semantics;
- source cropping;
- signed z-order;
- placement wire bytes;
- generation invalidation;
- cleanup ordering for non-relative placements;
- package dependency graph;
- registry capacity ceilings.

The public API baseline advances only for approved additive 1.13 members.
