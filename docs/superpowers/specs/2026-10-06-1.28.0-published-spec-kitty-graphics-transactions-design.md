# Icod.Terminal 1.28.0 Published-Spec Kitty Graphics Transactions Design

**Date:** 2026-10-06

**Status:** Approved by the maintainer on 2026-10-06

**Release:** `1.28.0`

**Baseline:** Merged and tagged `1.27.0` at
`485bedb014ab7b66391661c709833a6a4fa4afcc`

**Roadmap:**
[`Icod.Terminal-1.28.0-Development-Roadmap.md`](../../../Icod.Terminal-1.28.0-Development-Roadmap.md)

## 1. Intent and success criteria

Icod.Terminal currently waits for a correlated success response after every
persistent-animation mutation. The published Kitty Graphics Protocol requires a
response for image-data transfer carrying a nonzero image id, specifies failure
responses for frame composition, and documents animation controls without
promising a success response. Kitty 0.49.2 exposes the mismatch in two ways:

- it loses the starting image identity for a documented multi-chunk `a=f`
  continuation and therefore fails to acknowledge a stored frame; and
- it intentionally sends no success response for `a=a` animation controls.

Version 1.28 makes the protocol text the wire authority. It must:

1. preserve the documented `a=f` continuation grammar without repeating the
   image id as a Kitty 0.49.2 workaround;
2. stop waiting for success responses the published contract does not promise;
3. distinguish completed local output from correlated protocol acknowledgement;
4. retain definite failure, ambiguous commitment, late-response ownership and
   lifecycle behavior;
5. leave cells, damage, viewport state, fallback and atlas policy in
   Icod.DCurses; and
6. make the existing composition and regional-update primitives dependable
   enough to qualify a downstream compose-publish atlas.

The release succeeds when a caller can determine the confirmation strength of
every successful animation mutation, corrected implementations acknowledge the
published frame-transfer dialect, Kitty 0.49.2 fails in a bounded documented
lane, and the downstream atlas can be qualified without an `a=a` acknowledgement
dependency.

## 2. Governing rule

> Terminal emits the published protocol, waits only for responses the published
> contract guarantees, records stronger observed responses without universalizing
> them, and never upgrades output commitment into remote acknowledgement.

Published protocol grammar and response requirements are normative. Kitty source,
tests and live observations are implementation evidence. They may explain a
compatibility result; they may not silently alter Terminal's wire syntax.

## 3. Pinned authorities and implementation evidence

The protocol review is pinned so later upstream edits cannot silently change the
1.28 contract:

- published protocol document
  [`docs/graphics-protocol.rst`](https://github.com/kovidgoyal/kitty/blob/96693f4c090e9477b51ffa46aed4abdcef52d037/docs/graphics-protocol.rst)
  at source `96693f4c090e9477b51ffa46aed4abdcef52d037`, document blob
  `1473d807edd602e50d6b6f8834967bf18964e996`;
- stable implementation under qualification:
  [Kitty 0.49.2](https://github.com/kovidgoyal/kitty/releases/tag/v0.49.2),
  released 2026-10-01;
- confirmed defect report:
  [kitty #10599](https://github.com/kovidgoyal/kitty/issues/10599);
- upstream correction:
  [`b493a637b0573997f00423e8454f91a966ac96de`](https://github.com/kovidgoyal/kitty/commit/b493a637b0573997f00423e8454f91a966ac96de),
  committed after 0.49.2.

The reviewed protocol establishes these relevant rules:

- continuation chunks carry only `m` and optional `q`, except animation-frame
  continuations must also carry `a=f`;
- transmitting image data with a nonzero `i` causes a success or error response
  after the terminal attempts the transfer;
- `q=1` suppresses `OK` and `q=2` also suppresses failures;
- `a=a` defines frame selection, duration and playback controls but does not state
  that every successful control receives a response; and
- `a=c` requires `ENOENT`, `EINVAL` and, for storage expansion in Kitty,
  `ENOSPC` on the specified failure paths, while the reviewed text does not make
  a successful `OK` response the portable minimum.

## 4. Confirmed Kitty 0.49.2 classifications

| Area | Kitty 0.49.2 behavior | Classification | Terminal consequence |
| --- | --- | --- | --- |
| Final multi-chunk `a=f,m=0` continuation without repeated `i` | Stores the frame but loses response identity and sends no acknowledgement. | Confirmed implementation deviation, fixed after 0.49.2 by `b493a63`. | Keep the documented continuation. Timeout remains an ambiguous committed transfer and no frame token is published. |
| Repeated `i` on final continuation | Produces the missing response in 0.49.2. | Implementation-specific workaround that contradicts the documented continuation grammar. | Never emit it. |
| Successful `a=a` | Applies the control and sends no success response; upstream tests expect silence. | Implementation behavior within a published response ambiguity. | Do not install a success waiter. |
| Successful `a=c` | Sends `OK`. | Stronger observed behavior than the explicit minimum reviewed here. | Accept and report it as protocol acknowledgement without requiring every implementation to send it. |
| Failed `a=c` | Sends the documented failure response unless quiet policy suppresses it. | Required failure behavior. | Retain a bounded response window and classify a correlated failure definitively. |

The compatibility record must continue to name the exact Kitty version, source,
operating system, transport and configuration. A current-source fix is not called
released until a stable release containing it is identified and tested.

## 5. Public confirmation contract

### 5.1 Additive enum

Add one public enum without renumbering any existing enum:

```csharp
public enum TerminalControlMutationConfirmation {
    Unspecified = 0,
    OutputCommitted = 1,
    ProtocolAcknowledged = 2
}
```

The values mean:

- `Unspecified`: the result does not classify protocol confirmation. This is the
  compatibility value for existing local/native mutations and existing callers of
  `TerminalControlMutationResult.Success()`.
- `OutputCommitted`: the complete command passed Terminal's serialized write and
  flush boundary, but no correlated success response was promised or received.
- `ProtocolAcknowledged`: Terminal parsed a correlated protocol success response
  for this mutation. It necessarily implies prior output commitment.

The enum describes evidence available when the method returns. It does not claim
that the terminal rendered pixels, presented a frame atomically, or preserved the
state after a later terminal reset.

### 5.2 Additive result property

Add this public read-only property to `TerminalControlMutationResult`:

```csharp
public TerminalControlMutationConfirmation Confirmation { get; }
```

`Succeeded` remains source- and binary-compatible and continues to mean
`Status == TerminalControlStatus.Available`. It does not become a synonym for
`ProtocolAcknowledged`.

Existing `Success()` remains public and returns `Unspecified`. An internal
`Success(TerminalControlMutationConfirmation confirmation)` factory supplies the
two explicit protocol values to Terminal production code. Controlled unavailable,
unsupported and failed results always carry `Unspecified`; callers inspect
confirmation only when `Succeeded` is true.

No existing animation method changes its return type. In particular:

- `AddFrameAsync` still returns
  `TerminalControlResult<TerminalRasterAnimationFrame>`; an available opaque frame
  remains proof that the required frame-transfer acknowledgement was received;
- duration, selection, playback, composition and region-update methods continue to
  return `TerminalControlMutationResult`; and
- no raw action, image id, frame number, response policy or implementation profile
  becomes public.

### 5.3 Why the result type is extended

A graphics-specific replacement result would require incompatible return-type
changes or parallel methods for every animation mutation. Reinterpreting
`Succeeded` as remote acknowledgement would break existing output-only mutations.
An additive confirmation property is the smallest compatible shape that lets
callers distinguish the selected states.

## 6. Frozen action-response matrix

| Semantic operation | Wire action | Quiet value | Published response class | Completion behavior | Successful confirmation |
| --- | --- | --- | --- | --- | --- |
| Append full frame | `a=f` | default `q=0` | Required success or failure for transferred data with nonzero `i` | Register matcher before output and await correlated response. | `AddFrameAsync` publishes a token only after acknowledgement. |
| Replace frame region | `a=f` | default `q=0` | Required success or failure for transferred data with nonzero `i` | Register matcher before output and await correlated response. | `ProtocolAcknowledged` |
| Set frame duration | `a=a` | `q=2` | No response guaranteed | Serialize, revalidate, write and flush without a response waiter. | `OutputCommitted` |
| Select current frame | `a=a` | `q=2` | No response guaranteed | Serialize, revalidate, write and flush without a response waiter. | `OutputCommitted` |
| Stop playback | `a=a` | `q=2` | No response guaranteed | Serialize, revalidate, write and flush without a response waiter. | `OutputCommitted` |
| Run loading mode | `a=a` | `q=2` | No response guaranteed | Serialize, revalidate, write and flush without a response waiter. | `OutputCommitted` |
| Run normal playback | `a=a` | `q=2` | No response guaranteed | Serialize, revalidate, write and flush without a response waiter. | `OutputCommitted` |
| Compose frames | `a=c` | default `q=0` | Specified failures required; success response not required by the reviewed minimum | Register matcher before output. A correlated reply before the one-second response deadline is definitive; silence after committed output is successful local completion only. | `ProtocolAcknowledged` after `OK`; otherwise `OutputCommitted` after committed silence. |

`q=2` is deliberate for `a=a`. Those controls have no reviewed response contract,
and suppressing both success and failure replies prevents an implementation-specific
late reply containing only the shared image id from being misattributed to a later
frame transaction. Terminal does not use `q=2` for `a=f` or `a=c`, where response
information is required or useful.

Unknown or newly added animation actions fail closed in private policy tests. They
must not inherit a response class by default.

## 7. Completion and failure states

The runtime preserves five semantic states:

1. **Not committed:** no command byte crossed the existing commitment boundary.
2. **Output committed:** the complete command was written and flushed, but no
   correlated success response was guaranteed or received.
3. **Protocol acknowledged:** a correlated success response was parsed for the
   owning transaction.
4. **Definitely rejected:** a correlated protocol failure was parsed.
5. **Committed outcome uncertain:** bytes crossed the commitment boundary but a
   required result could not be established because of timeout, malformed
   correlation, endpoint loss, cancellation after commitment or output failure.

Only states 2 and 3 produce successful mutation results with explicit
confirmation. State 1 keeps current exception/controlled-result behavior. State 4
returns `Failed` or `Unavailable` according to the existing narrow error mapping.
State 5 retains existing exception and lifecycle/uncertainty behavior; it is not
converted into a successful result merely because some bytes were written.

Composition silence is the one intentional distinction: because a successful
reply is not part of the reviewed portable minimum, committed silence at the
ordinary one-second response deadline is state 2 rather than state 5. A timeout
before commitment remains a timeout.

## 8. Private policy and transaction structure

Add one exhaustive private policy vocabulary, kept out of the package surface:

```csharp
internal enum KittyGraphicsPersistentAnimationResponsePolicy {
    None,
    Optional,
    Required
}
```

The mapping is fixed by semantic operation, not terminal brand or version:

```text
full/partial frame transfer -> Required
animation control           -> None
frame composition           -> Optional
```

The encoder remains responsible only for published bytes. Session transaction
code selects the policy and owns correlation, commitment and lifecycle behavior.
No encoder branch reads `TERM`, a process name, terminal version, environment
variable or compatibility profile.

Replace the append-specific private commitment tracker with the operation-neutral
`KittyGraphicsPersistentAnimationEmissionState`. It records two monotonic facts:

```text
HasStarted       the first complete APC frame write succeeded; the terminal may
                 have observed a mutation
OutputCommitted  every APC frame write and the final flush succeeded
```

`OutputCommitted` implies `HasStarted`. A flush failure after `HasStarted` remains
a possibly committed failure even though it cannot produce the public
`OutputCommitted` confirmation. Append cleanup uses `HasStarted` to decide whether
frame-sequence certainty is lost. Optional-response composition returns successful
`OutputCommitted` only when the second flag is true.

## 9. Required-response transactions

Full-frame append and regional frame replacement continue through the existing
query transaction manager:

1. validate semantic inputs and current ownership;
2. reserve any append identity before output;
3. register the image-id matcher before emission;
4. acquire serialized control output;
5. revalidate generation, resource, animation and frame ownership immediately
   before the first byte;
6. emit all documented chunks without caller-cancellation truncation after
   commitment;
7. flush;
8. parse the correlated response; and
9. publish state/evidence only after acknowledgement.

For append, a committed timeout, malformed correlated response, cancellation or
transport failure rolls back the local reservation and marks the animation
sequence uncertain. The terminal may have allocated the next private frame number.
No retry or subsequent append is permitted on that resource.

For regional replacement, frame numbering remains known after a committed
failure, but the target pixels are uncertain. The method throws and its XML
contract continues to require caller-owned resource recreation before retrying.
Terminal does not add a hidden pixel-state cache or a new public pixel-certainty
state in 1.28.

Kitty 0.49.2's silent final continuation follows exactly these rules. It is not
special-cased: the required-response transaction times out, preserves late
response ownership, and marks append sequence certainty lost.

## 10. No-response animation controls

`a=a` duration, selection and playback commands bypass the query transaction
manager because no response completes them. Their path is:

1. perform existing validation and cancellation checks;
2. encode the command with `q=2`;
3. acquire the existing control-output gate with caller cancellation;
4. revalidate resource/generation/frame/sequence ownership under that gate;
5. write one complete APC frame and flush with `CancellationToken.None`; and
6. return `Success(OutputCommitted)`.

Cancellation remains effective while waiting for the output gate. Once emission
starts, caller cancellation does not deliberately truncate the APC frame. Write or
flush failure propagates and does not produce a successful result.

No `ProtocolResponse` capability evidence is recorded for these operations. A
successful write does not prove that the terminal understood or applied the
control. Existing verified persistent-animation evidence remains a prerequisite
for attempting the operation.

Sequence rules remain unchanged: stop is permitted after append-sequence
uncertainty; run/loading are not; known-frame selection and duration remain
caller-requested commands against still-known frame identities.

## 11. Optional-response composition

Composition keeps `q=0` so required failures and stronger success replies remain
observable. It uses the existing one-second persistent-raster response deadline and
late-response ownership:

- correlated `OK` before the deadline returns
  `Success(ProtocolAcknowledged)` and records protocol-response evidence;
- correlated `ENOENT` invalidates the resource and returns `Unavailable`;
- correlated `EINVAL`, `ENOSPC` or another well-formed failure returns `Failed`
  without fabricating resource loss;
- silence after `OutputCommitted` becomes true returns
  `Success(OutputCommitted)` and records no protocol-response evidence; and
- timeout before full output commitment, malformed correlation, write/flush failure,
  cancellation and lifecycle invalidation retain their existing exception or
  controlled-unavailable behavior.

The query manager continues to own a timed-out image-id response for its bounded
late-response interval. A late response is quarantined; it does not retroactively
change the already-returned confirmation or seed current-generation evidence.
The protocol has no per-command transaction id, so responses beyond the bounded
ownership interval cannot be authenticated as belonging to the old command. Tests
must preserve serialization and prove that owned late APC traffic cannot complete
the next transaction.

Composition preserves known frame identities after committed ambiguity. Callers
that need exact destination pixels recreate the resource from their own source
state; Terminal does not claim rollback or remote atomicity.

## 12. Correlation and response parsing

`KittyGraphicsPersistentAnimationResponseMatcher` continues to require:

- APC framing;
- Kitty Graphics `G` payload;
- the exact private image id;
- no image-number field; and
- no placement-id field.

The matcher cannot authenticate an action because the protocol response does not
echo one. This is why no-response `a=a` commands use `q=2`, why response-owning
operations remain serialized, and why late ownership remains mandatory.

Malformed correlated frames never become success. Wrong image ids, placement
responses, image-number responses and unrelated APC traffic remain available to
their correct owner or ordinary input handling. There is still one authoritative
input reader and no graphics-specific reader task.

## 13. Ownership and lifecycle revalidation

Every mutation revalidates immediately before output while holding the shared
output gate:

- the session still accepts output;
- the resource is current for the same generation;
- the animation state allows the requested operation;
- every supplied frame token belongs to that animation and remains current; and
- the relevant sequence rule still holds.

Losing ownership before first byte returns controlled `Unavailable` and emits no
command. Losing ownership after an acknowledgement returns controlled
`Unavailable` and does not publish evidence into the new generation. A correlated
`ENOENT` follows existing resource/descendant invalidation. Resource release,
explicit disposal, session invalidation and endpoint closure remain monotonic; no
operation resurrects state.

No new lock or output serialization domain is introduced. Required and optional
response transactions use the query manager's ambiguity gate plus shared output
gate. No-response commands use only the shared output gate because `q=2` removes
their response-ownership requirement.

## 14. Capability and operation evidence

`TerminalCapabilityEvidenceSource.ProtocolResponse` is recorded only when a
correlated protocol response was actually parsed in the current evidence
generation.

- acknowledged frame transfer may verify the persistent-animation backend;
- acknowledged regional replacement may verify its focused operation;
- acknowledged composition may verify frame composition;
- output-committed composition does not verify frame composition;
- output-committed `a=a` controls do not create protocol-response evidence; and
- absence of an optional success response never records unsupported evidence.

Update public XML that currently calls every focused raster operation
"acknowledged." `TerminalRasterOperation.FrameComposition` describes the semantic
operation; `InspectRasterOperation` remains evidence inspection, not proof that a
particular output-only composition was applied.

## 15. Compose-publish downstream direction

No new Terminal public atlas, batch or scene API is added. Existing opaque frame
tokens plus `ComposeFrameAsync` and `UpdateFrameRegionAsync` are sufficient for the
downstream experiment:

1. allocate a visible frame and scratch frame through acknowledged transfers;
2. compose visible into scratch;
3. apply bounded sparse region replacements to scratch;
4. compose scratch into visible; and
5. inspect every mutation result's confirmation strength.

This removes the hard dependency on a current-frame `a=a` success response. It
does not promise that several commands are remotely atomic or tear-free. DCurses
continues to own damage, tile cells, viewport state, fallback and repaint. If the
complete workload cannot meet correctness or performance requirements, DCurses
retains controlled ordinary FRAME or TEXT fallback.

Kitty 0.49.2 remains a negative lane when documented multi-chunk frame transfer is
required. A corrected Kitty build containing `b493a63` is the positive candidate.
This qualification floor is documentation and evidence, not a runtime version
branch.

## 17. Required automated coverage

### Public contract

- exact enum names and numeric values;
- `Confirmation` read-only property;
- existing `Success()` remains source-compatible and yields `Unspecified`;
- failure factories yield `Unspecified`;
- `Succeeded` remains status-based; and
- public animation signatures and private-identity exclusions remain unchanged.

### Encoder and policy

- single- and multi-chunk full-frame and regional `a=f` bytes remain documented;
- continuation chunks never repeat `i`;
- every `a=a` form contains `q=2`;
- `a=c` does not suppress responses;
- every known semantic action has one explicit policy; and
- unknown policy inputs fail closed.

### Transactions

- required `OK`, negative response, silence, malformed response, wrong identity,
  cancellation, write failure, flush failure and late response;
- no-response controls complete after flush without waiting or consuming unrelated
  APC/input;
- optional composition `OK`, documented failures and committed silence;
- no protocol evidence from output-only completion;
- response expectations register before bytes commit; and
- same-resource/cross-resource concurrency remains serialized without deadlock.

### Ownership and lifecycle

- stale/released/disposed resources and foreign/stale frame tokens fail before
  output;
- ownership changes while queued are rechecked under the output gate;
- append ambiguity loses sequence certainty;
- partial-update/composition ambiguity preserves frame numbers but not pixel
  certainty;
- `ENOENT` invalidates resource descendants; and
- late acknowledgement cannot seed a new evidence generation.

### Package and downstream

- identical public API snapshots for `net8.0`, `net9.0` and `net10.0`;
- source and fresh-package samples use only public API;
- package contents, XML, dependencies, licenses and deterministic checks pass;
- Windows, Linux and macOS unit/integration/package lanes pass; and
- DCurses qualifies ATLAS/FRAME/TEXT selection through its complete live workload.

## 18. Live qualification matrix

The minimum selected matrix is:

| Lane | Expected purpose |
| --- | --- |
| Kitty 0.49.2 | Negative multi-chunk `a=f` acknowledgement lane; positive output-only `a=a` behavior; exact deviation record. |
| Kitty build containing `b493a63` | Positive documented multi-chunk frame-transfer and compose-publish candidate. |
| Another available Kitty-protocol implementation | Portability check that no Kitty-brand/version assumption entered the contract. |
| Headless scripted transport | Deterministic response/no-response/correlation/lifecycle proof; never called rendering evidence. |

Each live report records exact terminal/source/package, OS, host/transport,
configuration provenance, UTC time, commands, confirmation results and operator
visible rendering separately. `NotRun`, `Unavailable`, `OutputCommitted`,
`ProtocolAcknowledged`, `Rendered` and `Failed` remain distinct.

## 19. Compatibility and release boundaries

- Preserve the stable 1.0.0 compatibility floor and every existing public member
  and enum numeric value.
- Retain C# 13 and `net8.0`, `net9.0`, `net10.0` on managed Windows, Linux and
  macOS.
- Retain `Icod.TermInfo 1.17.0` and `Icod.Timing 1.0.0` unless a separately
  reviewed defect proves a dependency change necessary.
- Use PowerShell 5.1-compatible packaging and cmd/sh launchers; add no Python or
  native helper.
- Preserve one authoritative input/query path, serialized output, bounded waits,
  late-response quarantine, generation ownership and deterministic cleanup.
- Keep image ids, frame numbers, actions, dictionaries and implementation profiles
  private.
- Do not infer support from terminal names, versions, environment variables,
  successful writes, missing optional replies or documentation alone.

## 20. Alternatives rejected

### Repeat the image id on continuation chunks for Kitty 0.49.2

This produces a response in that release but creates a private dialect contrary to
the documented continuation grammar. It hides the upstream defect and risks
interoperability with conforming implementations. Rejected.

### Wait unconditionally for every animation mutation

This preserves current code structure but makes successful `a=a` commands time out
on Kitty 0.49.2 and on any implementation that follows the published minimum.
Rejected.

### Treat flush completion as protocol acknowledgement

A local transport boundary cannot prove remote parsing, acceptance or rendering.
Rejected.

### Add terminal-brand/version behavior branches

Brand and version strings are unauthenticated, mediated transports can lie, and
the wire contract would fragment. Rejected.

### Replace every animation return type

New graphics-specific result types would break compatibility or duplicate the
public surface. The additive confirmation property expresses the missing fact with
less API regret. Rejected.

### Add a public compose-publish batch

The protocol cannot promise remote atomicity across the sequence, and performance
has not yet been measured under the real DCurses workload. Rejected for 1.28.

## 21. Explicit non-goals

Version 1.28 does not add image-file decoding, PNG/GIF/APNG policy, Indexed8
regional updates, gapless frames, absolute screen-coordinate placement,
pixel-within-cell placement, retained source-image replay, terminal-owned cells or
damage, automatic retry, resource reconstruction, a raw graphics API, a general
protocol-extension API, PTY hosting or unrelated non-graphics protocols.

It does not promise atomic multi-command presentation, successful rendering from
an `OK`, or portable composition acknowledgement. It does not qualify ATLAS from
ordinary FRAME fallback or from the persistent-resource color-flash sample.

## 22. Implementation and approval gate

The maintainer approved this design on 2026-10-06. The executable RED/GREEN task
sequence is recorded in
[`../plans/2026-10-06-1.28.0-published-spec-kitty-graphics-transactions.md`](../plans/2026-10-06-1.28.0-published-spec-kitty-graphics-transactions.md).

Design approval authorizes the implementation plan, not runtime changes. Each
runtime task begins with a failing test, records the witnessed failure, makes the
smallest conforming change, runs focused and broad verification, and commits one
coherent tranche. Implementation starts only after the maintainer reviews and
approves that plan.

Stable metadata, merge, tag, GitHub release and NuGet publication remain separate
maintainer decisions after implementation, exact-head CI and live acceptance.
