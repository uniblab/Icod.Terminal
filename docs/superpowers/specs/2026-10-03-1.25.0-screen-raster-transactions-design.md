# Icod.Terminal 1.25 Screen Raster Transactions Design

**Date:** 2026-10-03
**Status:** Proposed for review; exact public contract freezes at T2500
**Decision:** Add immediate raster output to the existing semantic screen transaction
**Baseline:** Published `Icod.Terminal 1.24.1`
**Consumer:** `Icod.DCurses 2.3` full-frame raster fallback

## Problem and boundary

`TerminalSession.DisplayRasterAsync(image)` already routes a single immediate image through verified ordinary Kitty graphics or Sixel. `TerminalScreenOutputTransaction` orders screen plans, text, hyperlinks, and persistent Kitty placeholder cells, but cannot contain an immediate raster. Calling `DisplayRasterAsync` between DCurses refreshes cannot give the renderer a single ordered transaction containing cursor movement, raster, overlay text, and final cursor restoration.

The separate persistent capability requires terminal-assigned nonzero image identity and supports resource/frame operations. Contour, Windows Terminal, and WezTerm observations in the DCurses 2.3 acceptance sample showed controlled text fallback when that persistent subset was unavailable. Ordinary raster capability must be verified independently; those observations do not prove Sixel availability in any of those terminals.

| Owner | Responsibility |
| --- | --- |
| Application | Source art and a complete current viewport image for each requested immediate repaint |
| DCurses | Cell placement, clipping, visible regions, overlays, damage, refresh ordering, and text fallback |
| Terminal | Verified ordinary raster backend selection, image adaptation/quantization, bounded encoding, screen transaction output, and failure certainty |
| TermInfo | Immutable capability data consumed through Terminal |

Terminal does not retain a viewport, cache source pixels for replay, infer support from terminal names, or emulate persistent Kitty state with Sixel. No native terminal call is added.

## Selected public shape

Add one method to the existing builder:

```csharp
public sealed class TerminalScreenOutputTransaction {
    public void WriteRaster(TerminalRasterImage image);
}
```

The call adds one immutable image item, using the existing `TerminalRasterImage` formats and bounds. It does not emit output, probe capability, promise screen coordinates, or report a selected backend. The caller places it between ordinary `TerminalScreenOperationPlan` cursor moves and other transaction items. Existing item-count and aggregate payload limits apply to the prepared image output. The T2500 public API gate freezes the precise XML remarks and payload accounting before implementation.

`CommitAsync` remains a single-use `ValueTask` operation. A missing verified backend, unsupported image semantics, an oversized prepared payload, or stale output epoch fails before the first transaction byte. Null input throws `ArgumentNullException` at addition; absent verified raster support and image semantics that the selected backend cannot preserve throw `NotSupportedException` at commit; aggregate payload overflow throws `InvalidOperationException`; stale output epoch or changed evidence throws `InvalidOperationException`. The method does not change `DisplayRasterAsync` or return a `TerminalControlMutationResult` from `CommitAsync`.

## Capability and preparation

The caller verifies `TerminalCapability.RasterGraphics` before creating the transaction. Commit does not probe while holding output or presentation gates. It resolves the existing ordinary raster operation from current generation evidence: verified Kitty first, otherwise verified Sixel. A terminal may support ordinary Kitty even when its persistent image-id probe failed; that path remains eligible. Sixel-only evidence never verifies persistent resources or placeholders.

Before any transaction output, prepare all raster items through the selected backend adapter. Sixel quantization and the entire Sixel payload, including raster attributes and DCS framing, must be validated before commitment. Kitty framing/chunks also need a bounded prepared representation or equivalent complete dry run so normal data/encoding failures cannot arise after the first byte. Count the encoded image data toward a fixed transaction budget and reject overflow before output. Hold no protocol payload after commit ends. The existing 64 MiB transaction application-payload ceiling is the initial budget target; T2500 tests exact counting and confirms whether the ceiling includes all encoded raster framing. No unbounded materialization is acceptable.

Preparation may be asynchronous only before output-manager reservations; it may not consume or race the authoritative input/query coordinator from within the commit's output gate. Revalidate generation, selected backend, and session output epoch under the existing commit gate immediately before first byte. A generation or evidence change after preparation fails before output rather than silently switching an already prepared payload.

No fallback is attempted after the first image byte. The ordinary backend order is inherited from Terminal routing; callers and DCurses never select Kitty/Sixel by name.

## Ordering and cursor semantics

The transaction emits plans, raster items, text, and presentation controls in caller order under one serialized output lease. Existing synchronized-output and temporary cursor-visibility options retain their cleanup rules. A raster item is emitted as one complete protocol object, followed by subsequent items in the same transaction. Cancellation is observed before commitment; it cannot truncate an in-progress DCS/APC object intentionally.

Immediate graphics have backend-specific current-position, clipping, scrolling, and post-display cursor effects. `WriteRaster` does not promise a portable resulting cursor position or clipping rectangle. A caller that emits text after a raster must add an independently valid cursor movement plan (planned with an unknown current position); it must likewise add an explicit final cursor movement when necessary. Terminal must not assume the raster left the cursor where it started. Full-screen rendering near the bottom/right edge may scroll or clip differently across terminals; DCurses must choose a conservative placement and qualify it physically.

Sixel's palette and transparency semantics remain those of `DisplayRasterAsync`; transparency is not a guarantee that a previous raster is erased. No automatic image mask, compositing, resize, scroll recovery, or text-over-raster guarantee is added by Terminal.

## Failure certainty

- Validation, no verified backend, unsupported format/alpha semantics, payload overflow, stale epoch, and generation change before output produce no transaction bytes.
- Once output begins, a write, flush, or cleanup failure leaves the remote screen uncertain. The transaction throws, advances the output epoch through the existing lease, and never retries the raster or switches backend.
- A complete local write is not a remote rendering acknowledgement. Success means the transaction was written and flushed, not that the terminal displayed pixels correctly.
- Synchronized-output or temporary cursor-visibility cleanup is attempted with `CancellationToken.None`; independent failures are aggregated under the current transaction rules.
- DCurses invalidates its physical-screen certainty after a committed failure and obtains a new full frame from the application for later repaint.

## Alternatives considered

1. **Direct `DisplayRasterAsync` between screen refreshes:** Reuses the codec but cannot order one frame's cursor, raster, and text within a screen transaction. Keep it for stand-alone raster display.
2. **Persistent-resource emulation backed by cached tiles:** Preserves sparse caller updates while changing pixel ownership and making Sixel appear to implement unsupported frame operations. Do not implement.
3. **A new raster-placement/session API:** Could specify stronger coordinates and clipping later, but those semantics need separate physical evidence. Reuse the screen transaction and its semantic cursor plans for this release.

## Qualification

Unit fixtures cover exact output order on both verified backends, Kitty preferred over Sixel, Sixel-only success, unverified/unsupported preflight, alpha/format rejection, large encoded payloads, epoch/generation races, cancellation, concurrent output, payload write/flush faults, synchronized cleanup, and post-raster cursor plans. Existing placeholder and `DisplayRasterAsync` behavior must remain unchanged.

A package-only sample constructs an immutable full frame and shows verification before transaction creation, absolute cursor planning, raster item, text, and final cursor movement. A TermInfo-free DCurses-facing witness compiles against the built package. Windows, Linux, and macOS test matrices, public API snapshots across net8/net9/net10, XML docs, dependency/license/security gates, and package checks qualify the exact PR head. Manual DCurses acceptance records physical Sixel alignment, overlay, resize, scroll, and exit behavior separately; CI cannot claim it.

## Release scope

Version 1.25 adds the screen transaction raster item and its focused preparation/hardening only. It does not add persistent Sixel resources, sparse frame mutation, framebuffer ownership, image decoding, pixel scaling, physical placement, terminal-independent clipping, arbitrary alpha compositing, scene/window/cell policy, frame batching, PTY hosting, or native platform calls. Publication follows implementation and exact-head qualification; this planning PR contains no runtime or package-version change.
