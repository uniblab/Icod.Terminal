# Icod.Terminal 1.16.0 — Persistent Raster Animation and Frame Lifecycle Design

**Date:** 2026-09-15  
**Status:** approved architecture; exact public spelling frozen by T160  
**Release:** `1.16.0`  
**Prior completed line:** `1.15.0` — Unicode Placeholder and Virtual Raster Placement

## 1. Problem statement

`Icod.Terminal 1.11` through `1.15` established a bounded persistent-raster ownership model:

```text
1.11  opaque terminal-resident resources and physical placements
1.12  source-pixel cropping and signed z-order
1.13  immutable-parent relative placement ownership
1.14  side-effect-free lifecycle observability
1.15  virtual placements and Unicode-placeholder rendering
```

The missing raster capability is animation: multiple terminal-resident frames attached to one image resource, per-frame timing, explicit frame selection, and terminal-driven playback.

The design challenge is not simply encoding Kitty animation commands. The harder requirement is to preserve Icod.Terminal's existing semantic boundaries:

- callers must not learn Kitty image ids or raw 1-based frame numbers;
- frame transfer and animation control must reuse the authoritative output/query path;
- persistent source pixels must not be retained for replay;
- ambiguous committed append operations must not cause guessed frame numbering;
- loss of animation-sequence certainty must not falsely invalidate an otherwise usable raster resource;
- layout, clipping, windows, cells, damage, and higher-level timeline policy must remain above Terminal.

Version 1.16 therefore adds a resource-owned animation-control layer and opaque animation-frame tokens while preserving existing resource/placement/placeholder semantics.

## 2. Governing principle

> Terminal owns animation protocol identity, frame-sequence certainty, timing commands, and serialized control; callers own source frames, presentation placement, and higher-level animation policy.

This is the animation analogue of the 1.15 placeholder rule. Terminal provides the safe protocol/lifecycle primitive; `Icod.DCurses` or applications decide what animation means in a scene, window, widget, or timeline.

## 3. Protocol basis

The Kitty Graphics Protocol adds animation by extending one already-created image.

The relevant protocol actions are:

```text
a=f  transfer animation frame data
a=a  control animation playback, frame timing, and current frame
a=c  compose one frame into another
```

Protocol reference:

<https://sw.kovidgoyal.net/kitty/graphics-protocol/#animation>

Important properties for 1.16 are:

- animation belongs to a single existing image;
- the original image data is frame 1/root;
- additional frames are numbered in append order;
- `a=f` can append a new frame or edit existing frame data;
- `z` is the frame gap in milliseconds;
- `a=a,c=N` selects the current frame;
- `a=a,s=1` stops playback;
- `a=a,s=2` runs in loading mode and waits at the tail for more frames;
- `a=a,s=3` runs normally and loops after the final frame;
- `v` controls loop count using protocol-specific encoding;
- the root frame defaults to zero gap and must have a positive gap assigned if it is to remain visible during terminal-driven playback;
- frame composition is a separate `a=c` facility.

Version 1.16 intentionally supports only the full-frame append/control subset. It does not expose existing-frame pixel editing, partial rectangles, prior-frame background canvases, gapless hidden composition frames, or `a=c` composition.

## 4. Why full-frame animation is the first release

A full animation implementation could expose the entire Kitty composition model immediately, but that would combine three distinct contracts:

1. frame-sequence ownership;
2. playback/timing control;
3. delta/composition geometry.

The first two are already substantial and naturally extend the 1.11–1.15 ownership system. The third introduces a second source/destination rectangle model, frame-edit semantics, alpha/replace composition policy, gapless hidden frames, and additional storage-failure behavior.

1.16 therefore freezes a narrower invariant:

> Every frame published by Terminal represents one successfully acknowledged full-size frame in one known append sequence.

Frame composition remains a later independent track after this invariant is proven.

## 5. Semantic ownership model

The approved semantic model is:

```text
TerminalRasterResource
    |
    +-- TerminalRasterPlacement
    |       ordinary or relative physical placement
    |
    +-- TerminalRasterPlaceholder
    |       virtual placement / text-grid anchor
    |
    +-- TerminalRasterAnimation
            resource-owned animation controller/view
            |
            +-- TerminalRasterAnimationFrame
                    opaque known-frame token
```

Animation does not create a new image resource or placement graph.

## 6. TerminalRasterResource remains the ownership root

`TerminalRasterResource` continues to own:

- terminal-resident image data;
- intrinsic source width and height;
- private Kitty image identity;
- session/generation association;
- physical placements;
- virtual placeholders;
- final terminal-side image deletion;
- `TerminalRasterOwnershipState` resource certainty.

The resource's original image pixels are animation frame 1/root.

Creating or accessing an animation controller does not re-upload the resource and does not create a second terminal image.

## 7. TerminalRasterAnimation is resource-owned, not a second disposable resource

The preferred `TerminalRasterAnimation` abstraction is a resource-scoped controller/view rather than an independent terminal ownership root.

There is exactly one logical animation sequence per raster resource.

The controller should not imply that disposing it deletes animation frames while preserving the image, because the protocol does not provide a clean semantic operation equivalent to destroying only the animation sequence and restoring the image to a pristine non-animated object.

Therefore the design preference for T160 is:

- animation lifetime follows the owning resource/session generation;
- the public animation controller is not independently `IAsyncDisposable`;
- resource disposal remains final cleanup authority;
- callers can stop playback explicitly without pretending that stop deletes frames.

If T160 finds a stronger API spelling that preserves these semantics, it may use it; it may not invent independent cleanup ownership that the terminal protocol cannot provide truthfully.

## 8. TerminalRasterAnimationFrame is an opaque token, not a disposable object

`TerminalRasterAnimationFrame` represents one frame whose protocol position is known with certainty.

It is not independently disposable in 1.16 because individual frame deletion is not part of the approved semantic contract.

A frame token is tied to:

- one animation controller;
- one owning raster resource;
- one session;
- one generation;
- one private protocol frame number.

The public API must not expose that private frame number.

A token from another animation/session/generation must be rejected locally before output.

## 9. Root-frame token

The base image is protocol frame 1/root and is already present before animation begins.

The approved design is to expose the root through the same semantic frame-token type as appended frames. This allows current-frame selection and frame-duration APIs to treat root uniformly without exposing `1` as a protocol identity.

The animation controller therefore has one known root frame immediately when it is created/accessed locally.

Obtaining that controller/root token emits no terminal traffic.

## 10. Candidate public shape

T160 owns exact names and signatures. The intended semantic shape is approximately:

```csharp
public sealed class TerminalRasterAnimation {
    public TerminalRasterAnimationFrame RootFrame { get; }
    public TerminalRasterAnimationState State { get; }

    public ValueTask<TerminalControlResult<TerminalRasterAnimationFrame>>
        AddFrameAsync(
            TerminalRasterImage image,
            TimeSpan duration,
            CancellationToken cancellationToken = default
        );

    public ValueTask<TerminalControlMutationResult> SetFrameDurationAsync(
        TerminalRasterAnimationFrame frame,
        TimeSpan duration,
        CancellationToken cancellationToken = default
    );

    public ValueTask<TerminalControlMutationResult> SelectFrameAsync(
        TerminalRasterAnimationFrame frame,
        CancellationToken cancellationToken = default
    );

    public ValueTask<TerminalControlMutationResult> StopAsync(...);
    public ValueTask<TerminalControlMutationResult> RunLoadingAsync(...);
    public ValueTask<TerminalControlMutationResult> RunAsync(...);
}
```

`TerminalRasterResource` exposes or returns its resource-owned animation controller through a compatibility-safe spelling frozen by T160.

The final API may use options/value objects for loop policy and timing if that reduces overload/API regret. The design requirement is semantic, not the draft spelling above.

## 11. Semantic capability

Version 1.16 adds one distinct semantic capability. The expected T160 candidate is:

```text
TerminalCapability.PersistentRasterAnimation = 11
```

All existing values remain unchanged.

The capability hierarchy is not inheritance; each value asks a distinct semantic question:

```text
RasterGraphics
    can display an ephemeral raster

PersistentRasterGraphics
    can own terminal-resident resource/physical-placement state

UnicodeRasterPlaceholders
    can own virtual placements and render semantic placeholder cells

PersistentRasterAnimation
    can own a known frame sequence and control animation playback
```

Verified persistent-raster support must not silently manufacture verified animation support.

## 12. Capability evidence

`InspectCapability(...)` remains side-effect free.

Terminal-brand or version heuristics are insufficient as public support truth.

T161 must audit whether any safe bounded animation-specific live query exists that does not create durable image/frame state. If no such primitive exists, `VerifyCapabilityAsync(PersistentRasterAnimation)` must retain controlled no-safe-probe semantics rather than fabricate one.

A successful real frame append is authoritative live evidence for that operation and may strengthen current-generation animation evidence according to T161's frozen rules.

Negative or ambiguous outcomes do not automatically become unsupported truth.

## 13. Full-frame transfer contract

Every 1.16 appended frame is a complete image frame.

The frame's intrinsic dimensions must equal the owning resource's intrinsic width and height.

The implementation may adapt existing supported raster storage forms through the reviewed persistent Kitty transfer path, but it must not:

- use file/temp-file/shared-memory transport silently;
- retain source-frame pixel copies after successful transfer for replay;
- accept partial rectangles;
- select a previous frame as a background canvas;
- edit existing frame pixels;
- expose blend/replace composition policy.

Locally knowable dimension mismatch is rejected before output.

## 14. Direct transfer and chunking

Frame data uses the same architectural commitments as persistent image creation:

- direct Kitty transfer;
- bounded chunk encoding;
- serialized output ownership;
- no interleaving another graphics operation inside one logical chunk sequence;
- cancellation effective before commitment;
- committed logical transfer not deliberately truncated by later caller cancellation;
- transport failure surfaced without automatic retry or backend switch.

Animation frame transfer differs because append order creates private frame identity. That difference drives the sequence-certainty rules below.

## 15. Frame-count bound

Animation bookkeeping must remain explicitly bounded.

The approved design target is a shared session ceiling of:

```text
maximum locally known animation frames  4096
```

Root frames of active animation controllers count against this ceiling.

This is independent of the existing 4096 physical+virtual placement ceiling because frames and placements are different terminal resources/identity spaces, but both ceilings are fixed and bounded.

There can be at most one animation controller per persistent resource, so the existing 256-resource ceiling also bounds the number of concurrent animations.

T160 may lower the 4096 frame ceiling if implementation-memory analysis proves a smaller value preferable, but it may not make frame tracking unbounded.

## 16. Positive duration contract

Version 1.16 exposes only visible positive frame durations.

Protocol `z=0` means ignored/unspecified and negative values create gapless frames. Those raw semantics are not exposed.

The preferred public representation is `TimeSpan` with:

```text
duration >= 1ms
duration <= Int32.MaxValue ms
exact whole-millisecond representation
```

T160 freezes whether non-integral milliseconds are rejected or converted by one documented deterministic rule. Silent platform-dependent rounding is forbidden.

Gapless/negative duration belongs to deferred composition support.

## 17. Root duration

The protocol root frame defaults to zero gap.

A root frame therefore cannot participate predictably as a visible frame in normal terminal-driven playback until a positive duration has been assigned.

The public API must allow setting the root-frame duration explicitly through the ordinary frame-duration operation.

Run/start validation may reject or return controlled unavailable state when required visible frames have no known positive duration, rather than silently choosing an application-level timing policy.

## 18. Current-frame selection

Callers may select any acknowledged known frame token as current.

The public method accepts a semantic frame token, not a frame number.

Validation rejects before output:

- default/invalid token;
- token from another animation;
- token from another session/generation;
- resource lifecycle no longer current enough for protocol mutation.

The internal implementation converts the token to the private 1-based protocol frame number only at the serialization boundary.

## 19. Terminal-driven playback modes

1.16 supports three semantic controls:

```text
Stop
RunLoading
Run
```

They map privately to the protocol stop/loading/normal-run states.

### Stop

Stops terminal-driven animation. The protocol resets its loop counter when stopped; public documentation must state this.

### RunLoading

Starts terminal-driven playback but waits at the last available frame for additional appended frames instead of looping to root.

This mode is specifically in scope so callers can stream animation frames over time without client-driven frame switching.

### Run

Starts normal terminal-driven playback. After the final frame, playback follows the configured finite/infinite loop policy.

## 20. Loop policy

Kitty's raw loop field is intentionally not exposed.

The public abstraction represents:

```text
Infinite
or
Finite(repeatCount >= 0)
```

where the semantic repeat count means additional repeats after the first traversal.

T160 freezes exact value-object/options spelling and maximum representable finite repeat count.

Terminal performs deterministic checked conversion to Kitty's private `v` encoding.

## 21. Client-driven playback is available through SelectFrameAsync, not a scheduler

A caller that wants client-driven animation can explicitly select frames using known frame tokens.

Icod.Terminal does not add a client-side timer/scheduler, background playback task, animation clock, frame queue, or automatic `Task.Delay` loop.

This avoids competing timing ownership and preserves the protocol's own terminal-driven animation facility.

Higher-level timing/timeline policy belongs to the caller or DCurses.

## 22. Sequence certainty is a distinct state axis

Frame append creates an implicit ordered protocol identity.

Suppose Terminal has acknowledged root plus frames 2..N. The next append should become N+1.

If an append commits to the transport and Terminal receives a successful correlated acknowledgement, N+1 becomes known and an opaque token may be published.

If the operation fails before commitment, no append was emitted and sequence certainty is unchanged.

If the operation may have reached the terminal but its final outcome cannot be proven, Terminal does not know whether the terminal now has N or N+1 frames.

That uncertainty must not be papered over.

## 23. Animation state model

Animation sequence certainty is not the same thing as raster-resource ownership.

The approved design therefore uses a distinct immutable animation-state vocabulary rather than overloading `TerminalRasterOwnershipState` to claim that the image resource itself is stale.

Conceptually the animation state must distinguish at least:

```text
Current
SequenceUncertain
Stale
Released
DisposedOwner
```

with semantic reasons sufficient to distinguish:

```text
None
FrameSequenceAmbiguous
SessionStateLost
ResourceMissing
ResourceReleased
ExplicitResourceDisposal
```

Exact public type/enum spelling is frozen by T160.

The central invariant is:

```text
resource.OwnershipState may remain Current / None
while
animation.State == SequenceUncertain / FrameSequenceAmbiguous
```

## 24. Behavior after sequence uncertainty

After append sequence certainty is lost:

- Terminal must not append another frame because it cannot know the next protocol frame number;
- Terminal must not start normal or loading-mode playback when doing so would expose an unknown tail as if the sequence were known;
- no automatic retry occurs;
- no automatic resource replay/re-upload occurs;
- no resource-missing state is fabricated;
- placements and placeholders may remain usable if the owning resource remains current.

Previously acknowledged frame tokens keep their known immutable protocol numbers. T160/T166 may permit idempotent control operations that target one such already-known token (for example explicit `SelectFrameAsync` or duration replacement) if they can be proven independent of the unknown tail.

`StopAsync` remains safe to expose after sequence uncertainty because it requires no guessed frame identity and can reduce terminal activity without pretending to restore sequence certainty.

There is no 1.16 in-place recovery operation that recreates certainty. Recovery is caller-owned resource recreation.

## 25. Control-operation ambiguity does not poison frame numbering

Animation control commands (`Stop`, `Run`, `RunLoading`, current-frame selection, duration replacement) do not append a new protocol frame number.

A committed control command can therefore fail ambiguously without losing knowledge of frame numbering.

The library:

- surfaces the control failure;
- does not auto-retry;
- does not invent a public claim that the terminal definitely applied or rejected the command;
- permits a later explicit caller command when local resource/sequence state otherwise allows it.

Repeated set/stop/select operations are treated as caller-requested fresh commands, not hidden retries.

## 26. Acknowledgement and response ownership

Animation operations reuse the existing authoritative graphics response/query infrastructure.

A frame token is published only after Terminal has enough correlated evidence to classify the append as successful under the reviewed protocol parser.

Wrong image identities, malformed responses, duplicate/invalid identity fields, unrelated APC traffic, and late responses must not satisfy another animation transaction.

No second animation-specific terminal reader is introduced.

## 27. Error classification

Locally knowable invalid requests fail before output.

Protocol/transport failures follow narrow semantic rules:

### ENOENT

A well-formed correlated response proving the owning image/resource is missing follows the existing resource-missing invalidation path. The animation becomes stale because its resource certainty is lost.

### EINVAL

Invalid-operation responses do not automatically mean the resource is missing. They are controlled operation failures unless a separate existing rule establishes lifecycle loss.

### Storage pressure

The protocol defines storage quotas for image/animation data and may fail operations under pressure. T167 must qualify the actual error forms encountered for full-frame append; 1.16 must not copy composition-only assumptions blindly.

### Timeout / late response / generic transport failure

These do not manufacture resource-missing truth.

For append specifically, the pre-commit versus possibly-committed distinction determines whether sequence certainty remains current or becomes uncertain.

## 28. Placement interaction

Animation alters the current pixels associated with one image resource. It does not create or reposition placements.

Existing ordinary and relative placements continue to refer to the same resource.

Starting/stopping animation or selecting a frame must not:

- create/delete a placement;
- mutate relative parentage;
- move the cursor;
- change placement crop/z-order/extents;
- change screen layout policy.

A resource may have zero, one, or many placements while its animation sequence exists.

## 29. Unicode placeholder interaction

Unicode placeholders also refer to the same resource image.

Animation therefore changes which resource frame is visible through existing placeholder cells without changing placeholder row/column identity or virtual-placement ownership.

1.16 must qualify that:

- frame append/control does not create/delete placeholder cells or placements;
- placeholder tokens remain resource/virtual-placement tokens, not frame tokens;
- disposing a placeholder does not delete animation frames;
- animation sequence uncertainty does not by itself stale a current placeholder;
- resource loss still propagates through both systems under established lifecycle rules.

## 30. Resource/session lifecycle

Animation and frame tokens are subordinate to the owning resource/session generation.

Required lifecycle behavior:

```text
session generation invalidation
    resource becomes stale
    animation becomes stale
    frame tokens no longer emit protocol identity

correlated resource ENOENT
    resource becomes stale / ResourceMissing
    animation becomes stale

intentional resource release
    animation becomes released

explicit resource-wrapper disposal
    animation becomes unavailable/disposed-owner consistently

animation sequence ambiguity only
    resource may remain current
    animation becomes SequenceUncertain
```

No animation state resurrection occurs within one resource generation.

## 31. Capacity model

1.16 adds bounded frame bookkeeping without changing existing resource/placement ceilings:

```text
maximum live persistent resources                  256
maximum live physical + virtual placements       4096
maximum relative-placement depth                    8
maximum known animation frames per session       4096   design target
```

A root frame counts when an animation controller is materialized for a resource.

The frame bound is local bookkeeping policy, not a promise about terminal storage capacity.

The terminal may reject additional frame data earlier because of its own storage quotas.

## 32. Memory ownership

`TerminalRasterImage` continues to own a bounded caller-snapshot appropriate to one immediate operation.

After an appended frame has been successfully transferred and the operation completes, animation bookkeeping retains semantic metadata only, not a copy of that frame's source pixels.

This means Terminal cannot silently reconstruct an animation after resource/session loss. That is intentional.

The caller/higher-level renderer owns any source-frame cache needed for future recreation.

## 33. Concurrency

Animation operations share the existing session output/query ownership model.

1.16 must qualify concurrency among:

- frame addition;
- timing replacement;
- frame selection;
- stop/run/loading control;
- resource disposal;
- session invalidation;
- state reads;
- unrelated application/graphics output.

No lock ordering may introduce a second output serialization domain.

Sequence state transitions must be monotonic and exact under races.

## 34. Cancellation

Caller cancellation remains effective before operation commitment.

After a logical frame transfer is committed, Terminal preserves committed-output integrity rather than intentionally truncating the transfer.

Cancellation after commitment does not justify blind replay.

For append, if cancellation/transport behavior leaves terminal acceptance ambiguous, the sequence-certainty rule applies.

## 35. DCurses boundary

`Icod.DCurses` remains responsible for:

```text
cells
windows
screen coordinates
clipping
scrolling
damage
layout
refresh/diff policy
higher-level animation timelines and scene semantics
```

`Icod.Terminal` is responsible for:

```text
terminal-resident frame sequence bookkeeping
opaque frame tokens
private frame numbers
frame transfer
positive frame timing
playback control
response correlation
sequence certainty
resource/session lifecycle propagation
serialized output
```

No DCurses source adoption is required for Terminal 1.16 release success. Stable downstream package qualification remains mandatory.

## 36. Security and trust boundary

Terminal graphics responses remain untrusted external input.

Successful correlation establishes transaction ownership, not trust in the terminal process.

Animation introduces storage-amplification risk because terminals may retain many frame images. Icod.Terminal therefore keeps:

- a local frame-count ceiling;
- existing raster pixel/byte bounds per transferred frame;
- bounded chunking;
- bounded response parsing;
- no unbounded append queue;
- no background producer;
- no retained pixel replay cache.

Applications remain responsible for deciding what pixel data is appropriate to disclose to the terminal.

## 37. Package/API identity boundary

The public 1.16 surface must not expose:

```text
Kitty image id
Kitty image number
Kitty 1-based frame number
a=f
a=a
a=c
raw s/c/r/z/v control keys
raw loop encoding
raw APC animation dictionaries
session generation id
production backend selection
```

Fresh package-only tests must enforce these exclusions where practical.

## 38. Explicit non-goals

Version 1.16 does not add:

- frame composition (`a=c`);
- partial/delta frame updates;
- editing existing frame pixels;
- previous-frame background canvases;
- gapless negative-duration composition frames;
- absolute screen-coordinate raster placement;
- pixel-within-cell positioning;
- GIF/APNG/image-file decoding/transcoding;
- audio/timeline synchronization;
- client-side animation scheduler/background timer;
- scene/window/cell/damage/layout ownership;
- retained hidden source-frame replay cache;
- automatic resource reconstruction after invalidation;
- terminal-authenticated passive existence queries;
- public raw Kitty frame/image identity;
- caller-selected Terminal production backend;
- PTY/ConPTY child-process hosting.

## 39. Testing strategy

Testing proceeds from semantic state outward:

1. freeze public API and identity exclusions;
2. capability evidence and no-invented-probe behavior;
3. pure bounded frame-sequence registry/root token;
4. exact full-frame encoding/chunking and successful append publication;
5. timing/current-frame controls;
6. terminal-driven playback controls;
7. lifecycle/sequence-ambiguity propagation;
8. capacity/concurrency/adversarial response hardening;
9. executable sample and downstream acceptance;
10. fresh package/XML/API/security/documentation qualification;
11. complete Windows/Linux/macOS stable release matrix.

Protocol-byte tests cover private encoding; state-machine tests cover sequence certainty; package tests cover the shipped semantic surface.

## 41. Release success definition

Version 1.16 is complete when a package consumer can:

```text
create one persistent raster resource
    -> access one resource-owned animation controller
    -> obtain its opaque root-frame token
    -> assign positive root timing
    -> append acknowledged full-size frames
    -> receive opaque tokens for those frames
    -> replace known-frame timing
    -> explicitly select a known current frame
    -> run loading-mode terminal playback while appending more frames
    -> stop playback
    -> run finite or infinite normal looping playback
    -> observe animation sequence certainty separately from resource ownership
    -> clean up deterministically through the existing resource/session lifecycle
```

without learning Kitty image ids/frame numbers, without a hidden source-frame replay cache, without a client-side background scheduler, and without moving layout/damage/scene ownership into `Icod.Terminal`.
