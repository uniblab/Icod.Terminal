# Icod.Terminal 1.15.0 — Unicode Placeholder and Virtual Raster Placement Design

**Date:** 2026-09-14  
**Status:** approved  
**Release:** `1.15.0`  
**Prior release:** `1.14.0` — persistent-raster lifecycle observability

## 1. Problem statement

`Icod.Terminal 1.11` through `1.14` established a backend-neutral persistent-raster stack:

```text
1.11  opaque terminal-resident resources and placements
1.12  source-pixel cropping and signed z-order
1.13  immutable-parent relative placement ownership
1.14  side-effect-free lifecycle observability
```

The next requirement is to let higher-level text-grid renderers display terminal-resident raster content as ordinary screen cells without exposing Kitty Graphics image ids, placement ids, Unicode placeholder encoding, SGR identity packing, or raw APC commands.

Kitty's Unicode placeholder model naturally separates an invisible virtual placement from the visible text cells that reference it. That separation aligns well with the existing Icod architecture if the protocol representation remains private.

Version 1.15 therefore introduces one new semantic ownership object: an opaque virtual raster placeholder handle from which higher-level code can derive semantic cell tokens.

## 2. Governing principle

> Terminal owns protocol identity and encoding; higher-level renderers own cells, cursor position, clipping, scrolling, damage, and layout.

The design must make Unicode raster placeholders usable by `Icod.DCurses` and other text-grid renderers without moving scene, window, cell, or virtual-screen policy into `Icod.Terminal`.

## 3. Protocol basis

The Kitty Graphics Protocol supports Unicode placeholder presentation through an invisible virtual placement created with `U=1` plus explicit rows and columns. Visible image instances are later materialized by writing ordinary Unicode text cells containing the image placeholder code point plus protocol-defined colors and combining marks.

The protocol documentation is maintained at:

- <https://sw.kovidgoyal.net/kitty/graphics-protocol/>
- <https://sw.kovidgoyal.net/kitty/_downloads/f0a0de9ec8d9ff4456206db8e0814937/rowcolumn-diacritics.txt>

Important protocol properties for this design are:

- a virtual placement has dimensions but no inherent screen location;
- visible placeholder instances are ordinary terminal text cells;
- row and column are encoded with combining diacritics;
- image identity is carried in foreground color plus an optional high-byte diacritic;
- placement identity is carried in underline color;
- the protocol permits inheritance from the cell to the left, but warns that this can fail under horizontal scrolling and overlapping images;
- a virtual placement cannot itself be relative;
- an ordinary relative placement may use a virtual placement as its parent.

Icod.Terminal therefore deliberately emits fully self-contained placeholder cells and does not use left-neighbor identity/coordinate shorthand.

## 4. Public ownership model

The approved semantic ownership tree is:

```text
TerminalRasterResource
    |
    +-- TerminalRasterPlacement
    |       ordinary or relative physical placement
    |
    +-- TerminalRasterPlaceholder
            acknowledged virtual placement
            |
            +-- TerminalRasterPlaceholderCell
                    semantic text-grid token
```

### 4.1 TerminalRasterResource

`TerminalRasterResource` continues to own terminal-resident raster data. It retains the 1.11–1.14 opaque identity, generation-scoped certainty, deterministic cleanup, and lifecycle observation contracts.

### 4.2 TerminalRasterPlacement

`TerminalRasterPlacement` continues to represent a physical protocol placement established either at the current text cursor or relative to one immutable parent placement.

Version 1.15 does not change ordinary placement semantics.

### 4.3 TerminalRasterPlaceholder

`TerminalRasterPlaceholder` is a new opaque public handle representing one acknowledged virtual placement.

It has:

- required rows and columns;
- no absolute screen position;
- no public image id;
- no public placement id;
- no public Unicode code-point encoding;
- no public raw APC command state;
- no backend selector;
- no scene/window/cell ownership.

The placeholder is tied to:

- one owning `TerminalRasterResource`;
- one `TerminalSession`;
- one session generation;
- one private virtual-placement identity.

### 4.4 TerminalRasterPlaceholderCell

`TerminalRasterPlaceholderCell` is a semantic immutable token representing one `(row, column)` cell of a specific `TerminalRasterPlaceholder`.

Its public row/column values do not constitute its complete identity. Internally it also retains an opaque association with the owning placeholder and session.

Two cell tokens with equal public row/column coordinates but produced by different placeholders are not interchangeable.

A placeholder cell is not independently disposable and is not an ownership root.

## 5. Candidate public API

T150 freezes exact public spelling. The approved semantic shape is expected to resemble:

```csharp
public sealed class TerminalRasterPlaceholderOptions {
    public int Columns { get; init; }
    public int Rows { get; init; }
}

public sealed class TerminalRasterPlaceholder : IAsyncDisposable {
    public int Columns { get; }
    public int Rows { get; }

    public TerminalRasterOwnershipState OwnershipState { get; }

    public TerminalRasterPlaceholderCell GetCell(
        int row,
        int column
    );
}

public readonly struct TerminalRasterPlaceholderCell {
    public int Row { get; }
    public int Column { get; }
}
```

`TerminalRasterResource` adds virtual-placement creation approximately equivalent to:

```csharp
public ValueTask<TerminalControlResult<TerminalRasterPlaceholder>>
    CreatePlaceholderAsync(
        TerminalRasterPlaceholderOptions options,
        CancellationToken cancellationToken = default
    );
```

`TerminalSession` adds typed placeholder-text output approximately equivalent to:

```csharp
public ValueTask WriteRasterPlaceholderCellAsync(
    TerminalRasterPlaceholderCell cell,
    CancellationToken cancellationToken = default
);

public ValueTask WriteRasterPlaceholderCellsAsync(
    ReadOnlyMemory<TerminalRasterPlaceholderCell> cells,
    CancellationToken cancellationToken = default
);
```

`TerminalRasterResource` adds a relative-placement overload approximately equivalent to:

```csharp
public ValueTask<TerminalControlResult<TerminalRasterPlacement>>
    CreateRelativePlacementAsync(
        TerminalRasterPlaceholder parent,
        int columnOffset,
        int rowOffset,
        TerminalRasterPlacementOptions? options = null,
        CancellationToken cancellationToken = default
    );
```

T150 may refine names, mutability, exact collection types, or argument spelling. It may not weaken the approved identity and responsibility boundaries.

## 6. Public identity boundary

Version 1.15 must not expose:

```text
Kitty image id
Kitty image number
Kitty placement id
virtual-placement protocol id
session generation id
U+10EEEE
row/column combining-mark table
image-id SGR color packing
placement-id SGR underline-color packing
U=1
raw APC payloads
backend selection
```

Callers receive semantic handles and semantic row/column tokens only.

`TerminalRasterPlaceholderCell` must not have a public constructor accepting protocol identity.

No public helper should accept or return raw Kitty image or placement identifiers.

## 7. Placeholder dimensions

Both placeholder dimensions are required.

The portable public contract is:

```text
Columns  1..256
Rows     1..256
```

The bound deliberately uses only the first 256 protocol-defined row/column combining indices even though the official table contains additional entries.

This produces a simple, deterministic portable contract and avoids depending on implementation-specific extensions to the diacritic table.

## 8. Placeholder options scope

`TerminalRasterPlaceholderOptions` is distinct from `TerminalRasterPlacementOptions`.

Version 1.15 does not add to placeholder options:

- source rectangles;
- cell-position coordinates;
- relative offsets;
- z-order;
- mutable parentage;
- animation/frame policy;
- clipping policy.

A virtual placement is a text-rendering prototype, not an ordinary physical placement.

## 9. Capacity model

Existing bounded persistent ownership remains one combined session-owned system:

```text
maximum live persistent resources                          256
maximum live physical + virtual placements               4096
maximum relative-placement depth                            8
maximum placeholder rows                                  256
maximum placeholder columns                               256
```

Virtual placements consume the existing placement-capacity budget rather than introducing a second independent 4096-object registry.

This reflects the fact that both physical and virtual placements consume private placement identity and session-owned lifecycle bookkeeping.

## 10. Private virtual-placement identity

Ordinary physical placement ids retain the existing private 32-bit identity domain.

Unicode placeholder cells carry virtual-placement identity through underline color, which provides 24 bits. Therefore virtual-placement ids are allocated from the private nonzero domain:

```text
1 .. 0x00FFFFFF
```

This is more than sufficient for the existing 4096-placement session ceiling and guarantees that every cell can encode the complete virtual-placement identity without relying on prior-cell shorthand.

Allocation remains:

- private;
- nonzero;
- collision-safe against current live virtual placements;
- monotonic where practical;
- wrap-safe.

The public API never exposes this distinction.

## 11. Self-contained placeholder cells

Every `TerminalRasterPlaceholderCell` must be independently encodable.

The encoded form always includes enough private information to reconstruct:

- complete image identity;
- complete virtual-placement identity;
- explicit row;
- explicit column.

The implementation will not omit repeated row, column, placement, or image components based on a previously emitted cell.

This is required so cell tokens remain safe under:

- clipping;
- sparse redraw;
- horizontal scrolling;
- vertical scrolling;
- overlapping rasters;
- damage-based rendering;
- arbitrary cell ordering;
- DCurses virtual-screen diffing.

## 12. Cell generation contract

Cell creation is synchronous, bounded, and side-effect free:

```csharp
TerminalRasterPlaceholderCell cell =
    placeholder.GetCell(row, column);
```

Local validation rejects rows or columns outside the placeholder's declared bounds.

Generating a token:

- emits no terminal bytes;
- acquires no output gate;
- registers no query;
- performs no capability verification;
- does not mutate ownership;
- performs no cleanup;
- performs no replay;
- does not select a backend.

## 13. Current-cursor emission contract

Placeholder-cell emission writes at the current text cursor position.

`Icod.Terminal` does not decide where the visible cell belongs on screen.

The caller remains responsible for:

- cursor movement;
- screen coordinates;
- clipping;
- scrolling;
- redraw order;
- window ownership;
- damage tracking.

The bulk emission API preserves caller order exactly.

The first implementation performs no cross-cell shorthand optimization.

## 14. Rendition boundary

Placeholder identity uses terminal foreground and underline colors as protocol channels.

Icod.Terminal must prevent those private identity colors from leaking into subsequent ordinary text.

Each independently emitted placeholder cell therefore terminates identity encoding with selective resets equivalent to:

```text
SGR 39  default foreground
SGR 59  default underline color
```

The implementation does not change background color solely for placeholder identity.

Other rendition attributes are preserved.

A higher-level renderer that requires a specific foreground or underline color after a placeholder cell is responsible for reasserting that cell's desired rendition, just as it would when transitioning between ordinary styled cells.

## 15. Lifecycle model

`TerminalRasterPlaceholder` reuses the 1.14 `TerminalRasterOwnershipState` vocabulary.

Required observable states include:

```text
successful creation
    Current / None

session generation invalidation
    Stale / SessionStateLost

correlated missing resource
    Stale / ResourceMissing

owning resource intentionally disposed
    Released / ResourceReleased

explicit placeholder wrapper disposal
    Disposed / ExplicitDisposal
```

`AncestorReleased` is not ordinarily applicable because a virtual placement cannot itself be relative.

Explicit wrapper disposal overrides that wrapper's observation with:

```text
Disposed / ExplicitDisposal
```

No stale/released/disposed placeholder becomes current again.

## 16. Token lifetime and emission validity

A `TerminalRasterPlaceholderCell` is not independently owned, but emission requires that its owning placeholder remain usable under the current session ownership model.

Before output, Terminal must reject tokens whose owning placeholder is:

- stale;
- released;
- explicitly disposed;
- from another session;
- from an invalid generation.

Such failures must not emit private stale identity.

## 17. Semantic capability

Version 1.15 should add one semantic capability, with exact spelling frozen in T150:

```text
TerminalCapability.UnicodeRasterPlaceholders
```

Expected numeric value:

```text
10
```

All existing `TerminalCapability` values retain their released numeric identities.

The semantic hierarchy is:

```text
RasterGraphics
    ephemeral raster display

PersistentRasterGraphics
    terminal-resident resource and physical-placement ownership

UnicodeRasterPlaceholders
    virtual-placement ownership and semantic placeholder-cell rendering
```

Placeholder support uses the persistent-resource machinery but must not be assumed merely because `PersistentRasterGraphics` is available.

## 18. Capability evidence and verification

`InspectCapability(...)` remains side-effect free.

Icod.Terminal must not invent a terminal-brand heuristic or fictional passive verification query for Unicode placeholders.

Generic Kitty graphics support does not automatically become `Verified` Unicode-placeholder support unless the reviewed protocol semantics justify that evidence level.

T151 must explicitly audit whether a safe bounded live verification primitive exists.

If no truthful probe exists, `VerifyCapabilityAsync(...)` must retain the existing controlled no-safe-probe semantics rather than emit invented traffic.

Actual placeholder creation acknowledgement remains authoritative for that creation transaction.

## 19. Virtual-placement creation

`CreatePlaceholderAsync(...)` uses the existing authoritative query/input transaction manager.

The internal request conceptually contains:

```text
placement creation
resource private image id
private virtual-placement id
U=1
columns
rows
```

A public `TerminalRasterPlaceholder` is published only after a successful correlated acknowledgement.

The library does not deliberately suppress replies using quiet mode because `TerminalSession` already owns bounded response correlation and can use acknowledgement as truthful transaction evidence.

## 20. Local validation

Locally knowable invalid operations are rejected before output.

This includes:

- null options;
- `Columns < 1`;
- `Columns > 256`;
- `Rows < 1`;
- `Rows > 256`;
- stale resource;
- disposed resource;
- wrong-session relative parent;
- exhausted combined placement capacity;
- invalid token coordinates;
- cancellation observed before commitment.

## 21. Response and transport errors

A correlated `ENOENT` denoting a missing owning image/resource follows the established missing-resource lifecycle rules.

Malformed replies, wrong identities, late replies, timeouts, or transport failure do not manufacture missing-resource truth merely because the operation failed.

If transport fails after placeholder-creation output commitment:

- no public placeholder handle is published;
- no blind retry occurs;
- no automatic backend switch occurs;
- no raster replay/re-upload occurs;
- the owning resource is not automatically declared missing without independent evidence.

Failure while writing visible placeholder text is ordinary committed text-output failure and does not automatically stale or dispose the virtual placement.

## 22. Relative-placement bridge

A physical `TerminalRasterPlacement` may use a `TerminalRasterPlaceholder` as its immutable parent.

The virtual placeholder itself may not be relative.

The relationship is:

```text
TerminalRasterPlaceholder
    virtual text anchor
        |
        +-- TerminalRasterPlacement
                physical relative placement
```

The existing relative-placement guarantees remain:

- immutable parentage;
- signed terminal-cell offsets;
- depth limit 8;
- resource lifetime distinct from parent lifetime;
- descendant-before-parent cleanup;
- no reparenting;
- `ENOPARENT`, `ECYCLE`, `ETOODEEP`, and `ENOENT` hardening.

Disposing/releasing a virtual parent releases dependent physical relative placements according to the existing placement-lifetime model.

The raster resource behind the placeholder remains independently owned unless separately disposed or invalidated.

## 23. DCurses boundary

`Icod.DCurses` remains responsible for:

```text
cells
windows
screen coordinates
clipping
damage
scrolling
layout
refresh ordering
virtual-screen diffing
```

`Icod.Terminal` is responsible for:

```text
virtual raster placement ownership
placeholder token production
protocol-private identity
placeholder encoding
acknowledgement correlation
lifecycle certainty
serialized terminal output
```

A primary 1.15 success criterion is that DCurses can eventually store a semantic placeholder-cell token without importing Kitty protocol identity or encoding rules.

No DCurses source adoption is required for the Icod.Terminal 1.15 release itself. Stable downstream package acceptance remains a release gate.

## 24. Concurrency

Placeholder ownership and token generation may be observed concurrently with resource/placeholder disposal and session invalidation.

The implementation must preserve:

- atomic `OwnershipState` observation;
- monotonic lifecycle transitions;
- no stale identity emission;
- bounded token generation;
- no lock dependency for `GetCell(...)` beyond what tests prove necessary;
- normal session output-gate serialization for emission;
- no second terminal reader.

Concurrency tests must use fixed, bounded work and constant or explicitly bounded memory.

## 25. Security and resource bounds

Terminal-controlled responses remain untrusted.

Version 1.15 requires explicit bounds for:

- virtual placement registry membership;
- placement ID allocation;
- placeholder dimensions;
- cell-token coordinates;
- bulk placeholder-cell count;
- encoded UTF-8 output size;
- correlated response parsing.

The library does not retain a second arbitrary source-raster copy merely to support Unicode placeholders.

Placeholder support introduces no file, temporary-file, or shared-memory transport.

## 26. Compatibility

Version 1.15 is additive over the stable 1.0 compatibility floor and the complete 1.14 public surface.

Existing consumers that never call placeholder APIs retain existing:

- ephemeral raster routing;
- persistent resource creation;
- ordinary placement creation;
- source crop and signed z-order;
- relative placement semantics;
- lifecycle observation;
- capacity limits;
- generation invalidation;
- cleanup behavior;
- no-replay guarantees;
- private protocol identity.

No existing public numeric enum value changes.

## 27. Explicit non-goals

Version 1.15 does not add:

- animation/frame lifecycle;
- absolute screen-coordinate raster placement;
- pixel-within-cell positioning;
- general scene graphs;
- window ownership;
- cell ownership inside Terminal;
- reparenting;
- automatic placeholder redraw after damage;
- tracking of emitted placeholder screen positions;
- terminal-authenticated object existence;
- hidden source-image replay;
- public graphics identities;
- public `U+10EEEE` encoding helpers;
- raw Kitty command construction;
- Sixel placeholder emulation;
- image decoding/transcoding;
- PTY/ConPTY hosting.

## 28. Release success definition

Version 1.15 is successful when a consumer can:

```text
create an opaque acknowledged virtual placeholder
    -> derive semantic row/column cell tokens
    -> store/reorder/clip those tokens independently
    -> emit them at caller-owned text-cursor positions
    -> render each token without left-neighbor inheritance
    -> observe placeholder lifecycle using the 1.14 state model
    -> use the virtual placeholder as parent for a physical relative placement
```

while never learning Kitty image/placement ids, placeholder codepoint/diacritic encoding, SGR identity packing, backend selection, or session generation identity, and while `Icod.Terminal` remains outside window/cell/layout/damage/scene ownership.
