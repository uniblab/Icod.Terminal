# Icod.Terminal 1.20.0 — Profile and Capability Decision Design

**Status:** Proposed implementation contract for the maintainer-selected release scope; no 1.20 implementation is accepted yet.

**Selected scope:** **3 + focused 6 + 10** — terminal-profile refinement, existing capability-verification hardening, and documentation/samples.

**Implementation roadmap:** [Icod.Terminal-1.20.0-Development-Roadmap.md](../../../Icod.Terminal-1.20.0-Development-Roadmap.md).

## Purpose and baseline

Help direct Terminal and DCurses consumers distinguish four different questions: what the selected profile advertises, whether a particular operation can be planned, what the live session has verified, and whether the required endpoint is available. Consumers should answer these questions using Terminal-owned contracts without interpreting TermInfo strings or guessing from terminal brands.

Start from released `v1.19.0`, merge commit `b3f7adf929d36ea654f2116ad6132781edc3fb3b` (PR #64). The existing public API fingerprint is `48975f2c42f6c544e9c574a9b3d79f7e2b7b3ecb10ab1a5a0b7067749e38e65d` on all three target frameworks. New profile members are expected to be additive; this fingerprint is the compatibility baseline, not a promised final 1.20 fingerprint.

The source already implements twelve `TerminalCapability` values. `VerifyCapabilityAsync` actively dispatches only `KeyboardReporting`, `RasterGraphics`, and `PersistentRasterGraphics`. The permanent capability guide and executable sample still describe the original nine-capability vocabulary and two verification choices. Correcting that drift is a required deliverable.

## Architecture and invariants

- Language: C# 13. Target frameworks: `net8.0`; `net9.0`; `net10.0`.
- Stable compatibility floor: `1.0.0`; preserve existing signatures, enum values, and documented behavior.
- Production dependencies: `Icod.TermInfo 1.16.0` and `Icod.Timing 1.0.0`. Optional integration tests/samples: `Icod.TermInfo.Inspection 1.16.0`. No dependency refresh is part of this scope.
- Use C#/.NET, PowerShell 5.1-compatible scripts, and cmd/sh. No Python or new tooling dependency.
- `TerminalProfile` remains an immutable description projection. Live observations do not mutate it.
- `InspectCapability` remains synchronous, side-effect free, and free of hidden query traffic.
- `VerifyCapabilityAsync` uses the existing input/query coordinator and explicit bounded probes. No second reader, background discovery, generic matcher API, or backend-selection API.
- Existing status dimensions and immutable snapshot behavior remain intact. A timeout alone is not authoritative negative support evidence.
- Planning stays opaque, side-effect free, parameter-sensitive, and session-bound. A non-null plan is not proof of successful physical terminal execution.
- Existing output commitment, presentation ownership, and generation-scoped resource rules remain unchanged. Consumers retain layout, retained cells, damage, physical-state assumptions, and recovery policy.

## Option 3 — Static screen advertisement

Add a small semantic advertisement surface to `TerminalScreenCapabilities`, created through `TerminalProfile.Create`. Reuse existing operation-kind enums for erase and shift operations. Do not add screen operations to `TerminalCapability`: the latter describes session support/evidence, not a parallel set of planner preconditions.

The proposed public additions, subject to T200 API review before coding, are:

```csharp
// On TerminalScreenCapabilities; immutable getter-only facts.
public bool AdvertisesCursorHome { get; }
public bool AdvertisesCursorRowAddressing { get; }
public bool AdvertisesCursorColumnAddressing { get; }
public bool AdvertisesCarriageReturn { get; }
public bool AdvertisesCursorUp { get; }
public bool AdvertisesCursorDown { get; }
public bool AdvertisesCursorLeft { get; }
public bool AdvertisesCursorRight { get; }
public bool AdvertisesScrollRegion { get; }
public bool AdvertisesErase(TerminalScreenEraseKind kind);
public bool AdvertisesCharacterShift(TerminalScreenCharacterShiftKind kind);
public bool AdvertisesLineShift(TerminalScreenLineShiftKind kind);
```

Keep existing `Supports...` members and their behavior. Explain their static-profile context without renaming them. Do not add a broad `SupportsAllCursorMoves` or `CanRender` flag: individual routes require different caller knowledge and parameters.

The new facts mean that at least one relevant capability representation is present in the description; they do not expand or validate every possible parameterization. Use the same presence convention as existing profile projection: absence is false; a present empty representation is still advertised. Parameterized or single-step alternatives can each advertise a directional/shift operation. Count-specific expansion, padding, work bounds, fallback choice, and exact plan cost remain planner responsibilities.

Freeze a table in T200 mapping each new member/enum value to the exact existing planner capability sources. Include all four erase kinds, all three character-shift kinds, and all four line-shift kinds. `AdvertisesCharacterShift(Erase)` must follow the existing parameterized erase-character route, without inventing a single-character fallback. Invalid enum values throw `ArgumentOutOfRangeException`; a default `TerminalScreenCapabilities` advertises none of the additions.

Do not duplicate planner algorithms in profile construction. Implement projection as bounded presence checks over the selected immutable description. Test record equality/hash behavior and default construction when adding backing state; do not accidentally make equality depend on the identity of an internal collection.

### Decision truth table

| Situation | Profile advertisement | Planner / live interpretation |
| --- | --- | --- |
| Capability absent | False for that representation/operation | Another existing route may still produce a plan; absence is not terminal-wide unsupported evidence. |
| Present valid representation | True | Planning still depends on parameters, required state, bounds, and padding. |
| Present empty representation | True | The existing planner decides whether a valid zero-byte plan exists. |
| Present malformed representation | True | Planning retains its existing safe rejection/error semantics; advertisement is not executable validation. |
| No absolute cursor address, but home/relative alternatives | Existing absolute flag false; relevant new route facts true | An existing fallback may plan the particular target. |
| Profile advertises support; endpoint redirected/unavailable | Static profile unchanged | Session endpoint availability can make the operation unusable. |
| Lifecycle invalidation/resume | Static profile unchanged | Current-generation live evidence expires; re-inspect/re-verify as appropriate. |

The sample must demonstrate both advertisement and an actual parameterized planner result. It must not use a false advertisement flag to skip all alternative planning paths.

## Focused Option 6 — Existing verification paths only

Keep this public entry point:

```csharp
public ValueTask<TerminalCapabilityStatus> VerifyCapabilityAsync(
    TerminalCapability capability,
    CancellationToken cancellationToken = default);
```

No new timeout overload, public verification outcome type, or new probe family is required. Capture and document the actual per-query deadlines and possible sequential probes at T200; do not describe a one-second internal query timeout as a one-second end-to-end guarantee. Existing Kitty keyboard and Kitty graphics query deadlines are one second each at the baseline.

| Capability | Included path | Required boundary |
| --- | --- | --- |
| `KeyboardReporting` | Existing Kitty keyboard support query/barrier | Verification observes support; it does not acquire a keyboard-reporting lease. |
| `RasterGraphics` | Existing Kitty/Sixel evidence and aggregate routing | Evidence for one backend must not falsely establish or negate another; one usable backend can satisfy the semantic capability. |
| `PersistentRasterGraphics` | Existing Kitty graphics support query | Sixel evidence alone does not establish persistent-resource support. |
| All other current values | Inspection-only return, after existing validation/cancellation rules | No invented verification traffic. In particular, placeholders and animation gain no passive existence/behavior probe. |

Required behavior: unavailable endpoints and decisive current live evidence short-circuit; pre-cancellation emits no query bytes; cancellation after commitment retains existing framing/response ownership; silence remains uncertainty; correlated malformed responses preserve documented errors; late/stale responses cannot complete an unrelated request or become evidence for a newer lifecycle generation. Static evidence survives lifecycle changes, and already-returned snapshots remain unchanged.

Concurrent calls must remain bounded and correctly correlated under existing serialization. This release does not promise one shared probe per group of callers or introduce a new query scheduler/cache. Change production code only for a reproduced defect in the included contract, with a focused regression test. If existing tests already prove a requirement, cite and retain them instead of adding duplicates.

## Option 10 — Consumer guide and executable sample

Extend `samples/Icod.Terminal.CapabilityPlanning.Sample`, retaining its existing `--verify` option:

- Default: describe the static profile, demonstrate representative side-effect-free screen planning, and print all twelve current capability statuses. No explicit live verification.
- `--verify`: explicitly verify the three supported paths, then re-inspect and explain the current statuses. State that query traffic is emitted.
- `--help`/`-h`: print usage before opening a session; succeed without a terminal.
- Unknown arguments: usage error and exit code 2 before opening a session. Success/help: 0; execution failure: 1; caller cancellation: 130 after cleanup.
- Explain `Support`, `EndpointAvailability`, `EvidenceKind`, and `IsUsable` separately. Report unknown/unavailable outcomes without claiming terminal incompatibility.
- Never create a second input reader or write raw protocol strings. No demo clipboard mutation, visible graphics upload, or keyboard-mode acquisition is needed for verification.

Extract the report/example routine into a source-linkable file so deterministic unit/package hosts execute the actual sample path. Source linking must leave the sample dependent only on Terminal; synthetic TermInfo setup stays in the test host. Extend the existing capability package verifier and run help in the existing sample verifier.

Update the capability guide, screen-output guide, architecture/compatibility/security guidance, root README, sample catalog and dedicated sample README. Cover the twelve-capability/three-probe table, advertisement versus plans, no-probe cases, lifecycle snapshots, timeout uncertainty, and practical fallback. Keep detailed historical release records intact.

## Exclusions and review boundary

No new keyboard protocol, operational protocol, endpoint API, public extensibility, animation composition, raster positioning, image decoding, PTY hosting, or query-router redesign. Cursor-visibility transaction composition remains deferred to a separate presentation-ownership design. No automatic recovery/replay, terminal-brand capability guessing, new public TermInfo types, or mandatory live probing.

T200 reviews the proposed additive names and source mappings before implementation. Any material contract change is recorded in this design and the roadmap before dependent work starts. A change requiring a new state owner or protocol family is deferred rather than silently included under “focused 6”.

## T200 reviewed source mapping and timing

The maintainer approved implementation after reviewing the planning PR. The nine properties and three methods above are retained. The following internal sources are implementation evidence, not public capability identifiers.

| Advertisement | Existing `StringCapability` sources (either alternative suffices) |
| --- | --- |
| CursorHome | `CursorHome` |
| CursorRowAddressing | `RowAddress` |
| CursorColumnAddressing | `ColumnAddress` |
| CarriageReturn | `CarriageReturn` |
| CursorUp / Down / Left / Right | corresponding `CursorUp` / `CursorDown` / `CursorLeft` / `CursorRight`, or the corresponding `...One` source |
| ScrollRegion | `ChangeScrollRegion` |
| Erase: ToEndOfLine / ToBeginningOfLine / ToEndOfScreen / Screen | respectively `ClearToEndOfLine`, `ClearToBeginningOfLine`, `ClearToEndOfScreen`, `ClearScreen` |
| CharacterShift: Insert / Delete | respectively `InsertCharacters` or `InsertCharacter`; `DeleteCharacters` or `DeleteCharacter` |
| CharacterShift: Erase | `EraseCharacters` only |
| LineShift: Insert / Delete | respectively `InsertLines` or `InsertLine`; `DeleteLines` or `DeleteLine` |
| LineShift: ScrollForward / ScrollReverse | respectively `ScrollForwardLines` or `ScrollForward`; `ScrollReverseLines` or `ScrollReverse` |

Keyboard and Kitty graphics verification each use a one-second query deadline with a Primary DA barrier. Sixel observation uses a one-second Primary DA query. Aggregate raster verification may perform Kitty followed by Sixel unless decisive evidence or the first barrier already resolves the required backend evidence. Serialization, transport completion, and sequential query work mean these are not an end-to-end one-second guarantee. The unchanged cancellation token permits caller-owned cancellation without adding a public timeout overload.

Existing lifecycle tests cover static evidence preservation, explicit invalidation, suspended/closed query ownership, pre-cancellation, and unavailable endpoints. Existing input/query suites cover fragmented, oversized, malformed, timed-out, and late responses. T203-T205 will qualify the public verification entry point and actual generation races using those foundations; passing existing cases is evidence, not a demand for duplicate production changes.
