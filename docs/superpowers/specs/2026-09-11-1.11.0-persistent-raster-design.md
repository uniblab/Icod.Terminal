# Icod.Terminal 1.11.0 — Persistent Raster Resources and Placements

**Date:** 2026-09-11  
**Release:** `1.11.0`  
**Status:** approved design; implementation pending  
**Base:** merged `1.10.0` mainline

## Purpose

Version 1.11 introduces session-owned persistent raster resources and placements without turning `Icod.Terminal` into a scene graph, exposing Kitty Graphics numeric identifiers, or weakening the established backend-neutral raster contract.

Versions 1.7 and 1.8 deliberately limited the public raster API to ephemeral `DisplayRasterAsync(...)` output. Version 1.10 then exposed protocol-neutral capability inspection and explicit bounded verification. Version 1.11 builds a new ownership domain on top of those foundations.

The release goal is intentionally narrow:

```text
create/upload one terminal-resident raster resource
create one or more placements for that resource
reposition/resize an existing placement
delete/dispose placements and resources deterministically
invalidate terminal-resident certainty across lifecycle-generation changes
```

## Design principles

1. Public resource and placement identity is opaque and semantic.
2. Kitty image ids, image numbers, and placement ids remain internal protocol details.
3. Persistent raster capability is distinct from ordinary raster-display capability.
4. Sixel remains a valid backend for ordinary `RasterGraphics`; it does not pretend to provide persistent-resource semantics.
5. The session owns persistent graphics bookkeeping and terminal cleanup while handles are alive.
6. No hidden source-image retention or automatic replay occurs across suspend/resume or explicit invalidation.
7. Lifecycle-generation changes invalidate terminal-resident certainty rather than inventing restoration.
8. Committed output follows the existing rule: after partial transmission, do not blindly replay, retry through another backend, or claim certainty about terminal state.
9. Registries and protocol data remain bounded.
10. 1.11 does not absorb DCurses cells/windows/layout/damage/scene ownership.

## Public capability model

Version 1.11 adds one semantic capability value:

```text
PersistentRasterGraphics = 9
```

This value is additive after the frozen 1.10 values `0..8`.

`RasterGraphics` continues to mean that the session can display a backend-neutral raster using a reviewed raster backend. `PersistentRasterGraphics` means that the session can create and manage terminal-resident raster resources and placements using the 1.11 ownership contract.

Therefore a session may truthfully report:

```text
RasterGraphics            Verified / usable
PersistentRasterGraphics  Unknown or Unsupported
```

when Sixel is available but the persistent Kitty subset is not verified.

`InspectCapability(...)` remains side-effect free. `VerifyCapabilityAsync(...)` may verify `PersistentRasterGraphics` only through an existing reviewed bounded Kitty Graphics support path; it does not invent a separate broad fingerprinting query.

## Public API shape

The intended public surface is:

```csharp
public sealed class TerminalRasterResource : IAsyncDisposable
public sealed class TerminalRasterPlacement : IAsyncDisposable
public sealed class TerminalRasterPlacementOptions

public ValueTask<TerminalRasterResource> CreateRasterResourceAsync(
    TerminalRasterImage image,
    CancellationToken cancellationToken = default
);

public ValueTask<TerminalRasterPlacement> CreatePlacementAsync(
    TerminalRasterPlacementOptions? options = null,
    CancellationToken cancellationToken = default
);

public ValueTask UpdateAsync(
    TerminalRasterPlacementOptions? options = null,
    CancellationToken cancellationToken = default
);
```

Exact property names and return/result details remain subject to the C110 API-regret gate, but the ownership model is frozen by this design.

### TerminalRasterResource

A resource represents one terminal-resident raster owned by one `TerminalSession` generation.

The public object:

- does not expose backend identity;
- does not expose image id/image number;
- does not expose mutable raster bytes;
- may create multiple placements;
- tracks whether its terminal-resident identity is still current for the owning session generation;
- is asynchronously disposable.

A resource cannot outlive the owning session meaningfully. After session disposal it is locally disposed/stale and cannot issue new terminal mutations.

### TerminalRasterPlacement

A placement represents one terminal placement of one resource.

The public object:

- does not expose Kitty placement id;
- belongs to exactly one resource and one session generation;
- may be updated in place semantically;
- is asynchronously disposable;
- becomes stale when the owning generation is invalidated.

Multiple placements may reference one resource.

### TerminalRasterPlacementOptions

The first release keeps placement policy narrow. Options initially cover only terminal-cell extent:

```text
Columns
Rows
```

Null/default options mean protocol/default intrinsic behavior.

Version 1.11 deliberately excludes absolute screen coordinates, pixel offsets, source rectangles, z-order, Unicode placeholders, relative placement, animation, and scene graph concepts.

## Placement positioning model

A placement is created at the terminal's current cursor position.

Creation/update uses Kitty's no-cursor-movement behavior so graphics placement does not itself advance or reposition the text cursor. Repositioning is therefore explicit at the application/session level:

```text
move terminal cursor through ordinary semantic terminal operations
update the existing placement
```

The same private placement identity is reused when updating a placement so the terminal replaces the existing placement rather than creating an unrelated public object.

This keeps coordinate policy outside `Icod.Terminal` and avoids duplicating DCurses screen/layout ownership.

## Internal Kitty identity strategy

Initial upload uses a private nonzero Kitty image number generated by the session. The terminal acknowledgement supplies the terminal-side image id used for subsequent operations.

The session keeps both identities internal:

```text
public TerminalRasterResource
    -> private resource token
        -> private Kitty image number
        -> acknowledged Kitty image id
```

Each placement receives a private nonzero placement id scoped to the owning resource/session registry.

Allocation must:

- skip zero;
- avoid collision with live registry entries;
- remain bounded;
- handle wraparound explicitly rather than relying on unchecked overflow.

The public API never promises numeric identity stability.

## Protocol operations

The 1.11 Kitty subset adds typed internal operations for:

```text
transmit resource without automatic display
create placement for existing resource
replace/update existing placement
remove one placement
remove all placements/resource data as required by resource disposal
```

All protocol construction remains typed and bounded. There is no public raw Kitty command dictionary or APC writer.

Persistent operations use direct transfer only. File, temporary-file, and shared-memory media remain excluded.

## Acknowledgement and correlation

Creation of a persistent resource requires a correlated acknowledgement establishing terminal-side identity before the resource becomes usable.

The existing one-reader/query architecture remains authoritative. Persistent graphics must reuse that path and must not create a graphics-specific reader.

A correlated Kitty response remains untrusted input. Correlation grants routing ownership, not trust. Existing parser bounds and malformed-response recovery remain applicable.

The resource is published to the caller only after the required acknowledgement succeeds.

## Commit and cancellation semantics

Before commitment:

- argument/resource validation is complete;
- capability/endpoint requirements are checked;
- caller cancellation is honored;
- session output-gate acquisition remains cancellable.

After the first persistent graphics frame commits:

- ordinary caller cancellation does not intentionally truncate the logical protocol transaction;
- the output gate remains held through the transaction boundary;
- partial transport failure is surfaced;
- the operation does not automatically replay;
- the operation does not switch to Sixel;
- terminal-resident certainty is not fabricated after an ambiguous partial failure.

If a create operation fails after partial committed output but before reliable acknowledgement, no usable public resource handle is returned.

## Resource and placement registries

`TerminalSession` owns bounded registries for live persistent resources and placements.

The registries provide:

- opaque internal identity;
- generation association;
- parent/child ownership;
- idempotent local disposal state;
- serialization of conflicting mutations;
- bounded enumeration for teardown;
- prevention of reuse while an identity is live.

The registry is bookkeeping, not a retained scene representation. It does not retain arbitrary source raster images for replay.

A concrete maximum live-resource and maximum live-placement count must be selected and tested before C113 is accepted. The limit must be public-behaviorally controlled rather than allowing unbounded growth.

## Parent/child lifetime rules

A resource may own zero or more placements.

Placement disposal:

1. atomically marks the placement unavailable for new mutations;
2. when generation certainty is current, emits targeted placement deletion;
3. removes local registry ownership even when the terminal deletion reports failure;
4. surfaces deletion failure to the disposing caller.

Resource disposal:

1. stops new placement creation;
2. closes/disposes all still-live child placements;
3. when generation certainty is current, removes terminal-side resource data;
4. removes local registry ownership;
5. aggregates cleanup failures without leaving locally reusable identities.

Disposal is idempotent with respect to local ownership.

## Lifecycle-generation semantics

Persistent terminal graphics are generation-scoped.

`InvalidateState()` and managed suspend/resume advance/invalidate the generation used for persistent-resource certainty.

After invalidation:

- existing resource and placement handles become stale;
- no automatic image replay occurs;
- no hidden source-image copy is retained merely to support replay;
- update/create-placement operations fail in a controlled manner;
- disposal performs local bookkeeping but does not emit stale numeric ids that may now refer to unrelated terminal state.

Static capability knowledge may remain valid according to the 1.10 model; terminal-resident object identity does not.

A future release may introduce explicit re-upload/rebind semantics, but 1.11 does not.

## Session teardown

`TerminalSession.DisposeAsync()` remains final cleanup authority.

While the persistent-graphics generation is still current, teardown closes persistent graphics before final terminal-output restoration completes. Child placements are deleted before parent resources.

Cleanup failures are accumulated with the session's existing restoration/disposal failure model rather than masking earlier failures.

If the generation is already invalid, teardown performs local registry closure without sending stale terminal identities.

## Concurrency

Resource and placement state transitions are serialized within their ownership objects/registry.

Required properties:

- two callers cannot successfully dispose the same live object twice at the protocol level;
- create-placement cannot race resource disposal into an orphaned public handle;
- update cannot race placement disposal into reuse of a freed placement identity;
- session disposal prevents new persistent mutations and drains accepted committed transactions;
- independent read-only public properties remain safe without terminal I/O.

The design should reuse existing session output/query synchronization where appropriate rather than creating a second global synchronization model.

## Security and privacy

Persistent raster data has the same confidentiality properties as ordinary raster output: it is sent to the attached terminal and may be observed or retained by that environment.

New security rules are:

- never accept caller-supplied raw Kitty image/placement ids;
- never expose a generic persistent Kitty command builder;
- bound resource/placement registries;
- validate all sizes/counts before commitment;
- treat acknowledgements as untrusted terminal input;
- do not use file/temp/shared-memory transports;
- do not retain raster source data beyond what the explicit operation requires;
- do not replay after lifecycle uncertainty or partial committed failure.

## Compatibility

Version 1.11 is an additive minor release.

It must preserve:

- the 1.0 stable compatibility floor;
- all existing public signatures and enum numerics;
- `TerminalCapability` values `0..8` exactly;
- ordinary `DisplayRasterAsync(...)` semantics;
- Sixel and Kitty ephemeral raster routing;
- the one-reader input/query/event model;
- capability-planning truthfulness and side-effect-free inspection;
- committed graphics output semantics;
- `net8.0`, `net9.0`, and `net10.0` package targets.

A new 1.11 public API baseline and fingerprint are required before release.

## Deliberate exclusions

Version 1.11 does not add:

- public Kitty image ids, image numbers, or placement ids;
- public backend selection;
- Sixel emulation of persistent resources;
- automatic replay/re-upload after resume;
- retained source-image caches for hidden restoration;
- source rectangles;
- z-order;
- Unicode placeholders;
- relative placements;
- pixel-coordinate placement;
- animation;
- image-file decoding;
- file/temp/shared-memory Kitty transports;
- cells, windows, layout, damage tracking, or a scene graph.

These exclusions are intentional API and ownership boundaries, not unfinished pieces of 1.11.

## Testing strategy

Qualification is layered.

### Protocol unit tests

Cover exact typed Kitty payloads for upload, placement, replacement, and deletion; numeric bounds; zero rejection; malformed/duplicate response fields; correlation; and chunk boundaries.

### Ownership tests

Cover resource/placement identity allocation, multiple placements, parent/child disposal, idempotent disposal, race boundaries, bounded registries, and stale-generation behavior.

### Session tests

Cover capability inspection/verification, redirected/unavailable endpoints, cancellation before commitment, transport failure after commitment, session disposal, lifecycle invalidation, and no replay.

### Compatibility/package tests

Cover exact public API baselines on all TFMs, fresh NuGet-only consumption, generated XML documentation, no direct exposure of backend numeric ids, and downstream `Icod.DCurses` acceptance.

### Cross-platform validation

Windows, Linux, and macOS Staging validation remains mandatory even though persistent Kitty Graphics itself is terminal protocol traffic rather than an OS-native graphics API.

## Release acceptance

1.11 is complete only when:

- C110–C119 are accepted;
- the final public API baseline is frozen;
- Architecture, Security/Privacy, Compatibility/Versioning, README, samples, and release notes agree;
- all supported TFMs expose one identical public surface;
- fresh NuGet-only package consumption succeeds;
- downstream acceptance remains green;
- one unchanged final PR head passes the complete Staging matrix.

Merge, `main` Release validation, tagging, GitHub Release creation, and NuGet publication remain explicit maintainer actions.
