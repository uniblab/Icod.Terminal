# Icod.Terminal 1.14.0 — Persistent-Raster Lifecycle Observability Design

**Date:** 2026-09-13  
**Status:** approved; T140 public API freeze next  
**Release:** `1.14.0`

## 1. Problem statement

`Icod.Terminal 1.11`–`1.13` established opaque terminal-resident raster resources and placements, source crop/z-order geometry, immutable relative placement parentage, graph cleanup, and generation-scoped certainty.

Internally, the library already knows when persistent ownership is current, when terminal certainty has been invalidated, and when a placement lifetime has ended because an ancestor placement or owning resource was released. Public callers currently learn much of that state only indirectly through later unavailable mutations or disposal behavior.

Version 1.14 exposes that lifecycle knowledge directly without exposing protocol-private identities and without pretending the terminal protocol supplies a passive authoritative object-existence query.

## 2. Governing principle

> Expose Terminal's current ownership certainty; do not claim to observe terminal state that the protocol cannot non-destructively prove.

The observation API reports library-owned lifecycle certainty. It does not authenticate the terminal and does not guarantee that a subsequent terminal operation will succeed.

## 3. Scope

The design applies to:

```text
TerminalRasterResource
TerminalRasterPlacement
```

It adds side-effect-free lifecycle observation only.

It does not add new persistent creation/update/delete operations, backend selection, protocol IDs, replay, scene ownership, or terminal-side existence probing.

## 4. Why not `ExistsAsync()`

The reviewed persistent graphics backend can acknowledge operations and return negative evidence such as missing resource or parent identities during transactions. It does not provide a passive read-only primitive that proves an arbitrary previously created terminal-resident image or placement still exists.

Therefore an API named or documented as authoritative remote existence would be misleading.

The supported contract is local certainty:

```text
what Icod.Terminal currently knows about this ownership handle
```

not:

```text
what the terminal can prove still exists right now
```

## 5. Public semantic model

The public surface exposes one immutable state snapshot rather than separate independently read status/reason properties.

Candidate T140 spelling:

```csharp
public enum TerminalRasterOwnershipStatus {
    Current,
    Stale,
    Released,
    Disposed
}

public enum TerminalRasterOwnershipLossReason {
    None,
    SessionStateLost,
    ResourceMissing,
    ParentPlacementLost,
    AncestorReleased,
    ResourceReleased,
    ExplicitDisposal
}

public readonly record struct TerminalRasterOwnershipState(
    TerminalRasterOwnershipStatus Status,
    TerminalRasterOwnershipLossReason LossReason
);
```

Candidate handle surface:

```csharp
public TerminalRasterOwnershipState OwnershipState { get; }
```

The exact names are frozen only in T140. The four semantic states, reason-bearing atomic snapshot, and no-I/O contract are architectural requirements.

## 6. State semantics

### 6.1 Current

The handle belongs to the current session generation, local ownership is still active, and no evidence has invalidated the terminal-resident identity required by the handle.

`Current` means usable under current library certainty, not remotely authenticated existence.

### 6.2 Stale

The handle object remains available to the application, but terminal-resident certainty is no longer sufficient for mutation or dependent ownership.

Typical causes:

- explicit session-state invalidation;
- lifecycle generation change;
- correlated missing-resource evidence;
- correlated missing-parent evidence affecting a placement subtree.

Stale state is irreversible.

### 6.3 Released

The public wrapper may still be reachable, but the local ownership represented by it ended because another owner released the underlying placement relationship.

Primary cases:

- ancestor placement disposal removes a relative descendant;
- owning-resource disposal removes its placements;
- a resource-disposal cascade removes cross-resource descendant placements whose lifetime depends on the released subtree.

`Released` is a local lifetime fact and is intentionally distinct from `Stale`, which represents lost terminal certainty.

### 6.4 Disposed

The public wrapper itself has been disposed by its caller.

The observation property remains safe to read after disposal. Disposal is terminal for the public wrapper and never resurrects another state.

## 7. Reason semantics

### None

Required when status is `Current`.

### SessionStateLost

Terminal state knowledge was invalidated by explicit invalidation or a session lifecycle transition. No public generation number is exposed.

### ResourceMissing

Correlated evidence invalidated the affected persistent raster resource identity and dependent placement certainty.

### ParentPlacementLost

Correlated missing-parent evidence invalidated the affected placement subtree without automatically declaring the parent's raster resource missing.

### AncestorReleased

A placement lifetime ended because an ancestor placement was intentionally released/disposed.

### ResourceReleased

A placement lifetime ended because the raster resource owning that placement was intentionally released/disposed.

### ExplicitDisposal

The public wrapper itself was disposed.

Reason categories are semantic and backend-neutral. Raw protocol error text is never exposed as the lifecycle API.

## 8. Atomic observation

State and reason must be published atomically.

A caller must never observe combinations such as:

```text
Current + ResourceMissing
Released + None
Disposed + ParentPlacementLost
```

unless explicitly permitted by the final T140 state table.

The implementation should prefer one packed internal lifecycle value read/written through atomic/volatile operations, from which the immutable public snapshot is constructed.

The internal storage strategy is not public API.

## 9. Monotonicity

Lifecycle state never resurrects terminal certainty.

Allowed high-level transitions:

```text
Current  -> Stale
Current  -> Released
Current  -> Disposed
Stale    -> Disposed
Released -> Disposed
```

Forbidden transitions include:

```text
Stale    -> Current
Released -> Current
Disposed -> Current
```

Existing invalidation/cleanup behavior remains authoritative if an implementation path needs a more specific internal transition; T141 must map that path to one truthful public state without resurrection.

## 10. Resource/placement lifetime distinction

The 1.13 two-axis model remains unchanged:

```text
resource ownership axis:
TerminalRasterResource -> placement uses this raster resource

placement lifetime axis:
TerminalRasterPlacement parent -> relative descendant lifetime
```

Required public-observation example:

```text
Resource A     Current
  Placement A1 Current
Resource B     Current
  Placement B1 Current, relative to A1

Dispose A1
  Placement A1 Disposed
  Placement B1 Released / AncestorReleased
  Resource B    Current
```

A new placement may still be created from Resource B after the cascade if no independent evidence invalidated Resource B.

## 11. Side-effect-free contract

Reading lifecycle state must never:

- write terminal bytes;
- allocate/register a terminal query;
- acquire the output gate;
- verify capabilities;
- mutate registry ownership;
- trigger cleanup;
- re-upload/replay raster content;
- perform terminal-brand/backend selection.

The observation operation is synchronous and bounded.

## 12. Interaction with acknowledged operations

Acknowledged creation publishes a public handle only after success, so newly returned handles begin `Current`.

Placement geometry updates do not change lifecycle state on success.

Rejected/failed updates do not invent lifecycle loss unless the correlated response carries evidence whose existing semantics already invalidate certainty.

Relative-offset state still commits only after successful acknowledgement.

Late acknowledgements cannot resurrect stale/released/disposed ownership.

## 13. Interaction with negative terminal evidence

### Missing resource

Existing narrow missing-resource invalidation remains authoritative. The affected resource becomes stale; dependent placement certainty is invalidated according to current ownership rules; unrelated resources remain unchanged.

### Missing parent

Existing missing-parent semantics remain authoritative. The affected placement subtree becomes stale; the raster resource that happened to own the parent placement is not automatically declared missing.

### Other controlled failures

Controlled failures that do not establish ownership loss must not manufacture a lifecycle reason merely because the operation failed.

## 14. Interaction with disposal

Disposal remains locally idempotent.

The wrapper publishes `Disposed / ExplicitDisposal` as its final public state regardless of whether best-effort terminal cleanup later reports a transport failure, because the local wrapper is no longer usable/retriable under the existing disposal contract.

When an ancestor/resource disposal releases another placement before that placement wrapper is explicitly disposed, that descendant reports `Released` until its wrapper is later disposed.

## 15. Interaction with session invalidation

`TerminalSession.InvalidateState()` and lifecycle transitions that invalidate generation-scoped terminal certainty mark current persistent handles stale according to existing graph/resource rules.

No source pixels are retained for recovery. No automatic rebind/re-upload occurs. Public observation simply makes the resulting certainty state visible.

## 16. Concurrency

Lifecycle reads may occur concurrently with create/update/dispose/invalidation work.

The implementation must guarantee:

- thread-safe observation;
- atomic state/reason pairing;
- monotonic state transitions;
- no deadlock with output/query locks;
- no state resurrection through late response handling;
- no unbounded allocation/synchronization cost for reads.

Concurrency qualification is a dedicated T146 tranche rather than an incidental test add-on.

## 17. Capability model

Version 1.14 adds no new `TerminalCapability` merely to expose local lifecycle state.

`PersistentRasterGraphics` remains the capability governing persistent terminal-resident ownership operations.

Lifecycle observation is local state inspection and is available whenever a resource/placement wrapper exists, including after it becomes stale/released/disposed.

## 18. TermInfo boundary

`Icod.TermInfo` and `Icod.TermInfo.Inspection` continue to own static semantic planning/evidence based on immutable terminal description.

`Icod.Terminal` owns live lifecycle certainty for handles it created.

Version 1.14 does not move live handle-state observation into TermInfo and does not add an Inspection production dependency.

## 19. DCurses boundary

`Icod.DCurses` remains the owner of cells, windows, layout, damage, virtual-screen state, and higher-level refresh policy.

1.14 enables downstream consumers to react to persistent-raster lifetime transitions more explicitly, but does not require DCurses source adoption for release success. Stable package acceptance remains the required downstream witness.

## 20. Security and privacy

Lifecycle observation reveals only local semantic state already held by the process.

It does not expose:

- private image ids;
- private placement ids;
- parent protocol identities;
- terminal generation numbers;
- source raster pixels;
- terminal brand/backend selection.

A `Current` state is not authentication and must never be documented as such.

## 21. Testing strategy

Testing proceeds from semantic state transitions outward:

1. internal transition-table tests;
2. resource state tests;
3. placement state tests;
4. reason propagation tests;
5. depth/branch/cross-resource graph tests;
6. concurrency/memory-model tests;
7. zero-output/no-query inspection tests;
8. package/API/XML/sample tests;
9. downstream Stable 1.x package acceptance;
10. final Windows/Linux/macOS release matrix.

Every public lifecycle state/reason must have a direct test witness.

## 22. Non-goals

Version 1.14 does not add:

- passive remote `ExistsAsync()`/`VerifyExistsAsync()` semantics;
- terminal-authenticated existence;
- mutating reconciliation probes as ordinary inspection;
- automatic replay/re-upload;
- hidden source-image caching;
- public generation or protocol ids;
- backend selection;
- reparenting;
- Unicode placeholder/virtual placements;
- animation/frame lifecycle;
- absolute screen coordinates;
- pixel-within-cell placement;
- scene/window/cell/layout ownership;
- image decoding/transcoding;
- PTY/ConPTY hosting.

## 23. Compatibility

The release is additive over the stable 1.0 compatibility floor and published 1.13 API.

Existing consumers that never inspect lifecycle state continue to observe the existing creation/update/disposal behavior and wire encoding.

No 1.13 placement/resource capacity, graph-depth, acknowledgement, cleanup, or generation-scoped certainty guarantee is weakened.

## 24. Release success definition

1.14 is complete when consumers can synchronously inspect a persistent raster resource or placement and receive one atomic, backend-neutral, side-effect-free description of Terminal's current ownership certainty and semantic loss/release reason; relative placement lifetime loss remains distinguishable from independent raster-resource lifetime; and no protocol-private identity, invented terminal-existence guarantee, replay behavior, or higher-level layout ownership is introduced.
