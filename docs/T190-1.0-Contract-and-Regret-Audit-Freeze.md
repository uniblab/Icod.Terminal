# T190 — 1.0 Contract and Regret-Audit Freeze

**Release:** `Icod.Terminal 1.0.0-rc1`  
**Base:** published `0.18.0` merged to `main` at `c0f0ff482c8bb0d358c4fcb38e454d717b1b6f1c`  
**Purpose:** freeze the final pre-1.0 decision criteria before any public-contract correction

## 1. Why T190 exists

`0.18.0` established a heavily tested behavioral baseline. `1.0.0-rc1` has a different responsibility: decide which parts of that pre-1.0 surface are suitable to support as a durable 1.x contract and make those decisions discoverable without reconstructing eighteen release histories.

T190 therefore precedes all rc1 API or documentation corrections.

No public API should be renamed, removed, broadened, or added during rc1 merely because a different design is aesthetically preferable. A change requires a concrete long-term support reason.

## 2. Decision classes

Every audit observation must be classified as one of:

### A — freeze as-is

The API/behavior is coherent, testable, documented or straightforward to document, and supportable throughout 1.x.

### B — documentation defect

The runtime contract is acceptable, but XML documentation, README/sample guidance, package metadata, or permanent documentation is incomplete, stale, contradictory, or overly release-specific.

Prefer documentation correction over API change.

### C — test/acceptance defect

The contract is supportable but an important invariant lacks direct regression/package/downstream proof.

Prefer tests or acceptance expansion without surface change.

### D — final pre-1.0 API correction

The existing public surface is materially misleading, duplicate, unsafe, impossible to support compatibly, or located at the wrong abstraction layer.

Any D-class change must document:

- the concrete regret if left unchanged;
- compatibility impact;
- migration path;
- why documentation alone is insufficient;
- why deferring to 2.0 would be worse than correcting before 1.0.

### E — defer beyond 1.0

A desirable feature or cleanup is not necessary to support the existing contract safely and coherently. It is not rc1 work.

## 3. Audit domains

The complete audit shall cover:

| Domain | Questions |
| --- | --- |
| Session construction | Are ownership, endpoint, interactivity, and initialization guarantees obvious and supportable? |
| Endpoint/control model | Are platform-specific observations represented truthfully? |
| Terminal modes | Are native snapshots vs semantic policy separated correctly? |
| Lifecycle | Are suspend/resume/invalidation/termination/disposal semantics explicit? |
| Input model | Are text/key/mouse/focus/paste semantics stable and unsurprising? |
| Modern keyboard | Are negotiated Kitty semantics and xterm decode-only compatibility sufficiently abstracted? |
| Query routing | Are correlation, timeout, cancellation, ambiguity, and late ownership supportable? |
| Presentation | Are reversible screen/keypad/cursor leases coherent? |
| Semantic output | Are protocol APIs semantic, bounded, and non-overlapping? |
| Color/state ownership | Are observation, scoped ownership, reset-policy, and restoration distinct? |
| Results/exceptions | Are unavailable/unsupported/failure/cancellation distinctions consistent enough for 1.x? |
| Concurrency | Are ordering/serialization guarantees part of the contract where callers depend on them? |
| Security/privacy | Can every metadata/output API explain disclosure or execution risk accurately? |
| Packaging | Do NuGet metadata, XML docs, README, TFMs, dependency versions, and validation agree? |
| Samples | Do examples teach current best practice rather than historical release features? |
| Downstream | Can `Icod.DCurses` consume the frozen contract without private terminal mechanics? |

## 4. Frozen architectural boundaries

Unless T190 discovers a D-class defect, rc1 retains these boundaries:

- `Icod.TermInfo` owns immutable terminal capability data and expansion;
- `Icod.Terminal` owns live endpoint/session state, input, queries, lifecycle, semantic terminal output, and reversible terminal state;
- `Icod.DCurses` owns virtual-screen/cell/window/refresh policy;
- future `Icod.Pty` remains adjacent and optional rather than a dependency of `Icod.Terminal`;
- application command policy remains above the terminal substrate.

## 5. Frozen safety principles

The following are presumptively permanent 1.0 rules:

- no generic raw escape-sequence writer as the normal API;
- no arbitrary OSC/vendor command dispatcher;
- no blind activation of terminal state that cannot be observed or restored truthfully;
- exact captured-state restoration where ownership claims require it;
- semantic APIs above native flag manipulation for ordinary consumers;
- bounded incremental parsing;
- one authoritative input reader/query correlation path;
- pre-commit cancellation emits nothing where the contract promises atomic framing;
- post-commit operations do not invent compensating traffic unless the owning contract defines rollback;
- state uncertainty is surfaced rather than silently converted into believed success;
- platform differences remain observable rather than fabricated.

## 6. Compatibility policy to freeze during rc1

T190 starts from these presumptions:

- `net8.0`, `net9.0`, and `net10.0` remain supported for 1.0;
- vendor end-of-support alone is not sufficient reason to remove a TFM during rc1;
- public enum numeric values remain stable unless a D-class defect is demonstrated;
- public API removed or renamed during rc1 requires migration guidance;
- behavior explicitly frozen in 0.18 should not change silently;
- package-only consumers and real DCurses acceptance remain mandatory release evidence.

T195 will turn these presumptions into permanent consumer-facing compatibility/versioning documentation.

## 7. Documentation authority policy

Historical documents remain valuable evidence, but rc1 must end the need to search tranche notes for current truth.

Permanent documents created by T191–T195 become the primary supported-contract authorities. Versioned roadmaps and `Txxx` records remain historical/design records and must not contradict permanent documentation.

Stale authorities are defects. Known examples at T190 start include:

- `Icod.Terminal.csproj` package release notes still describe 0.16.0;
- the original `Icod.Terminal-Development-Roadmap.md` still presents a much earlier development state;
- `samples/README.md` is useful but remains heavily organized around historical release numbers.

These observations are B-class until the deeper audit proves otherwise.

## 8. T190 exit criteria

T190 closes only when:

1. the public API has been inventoried by contract domain;
2. every proposed API correction is classified A–E;
3. any D-class correction has an explicit written rationale and migration impact;
4. the permanent-document target set is confirmed;
5. stale repository/package/sample authorities have assigned cleanup tranches;
6. no feature expansion has entered rc1 by accident;
7. the exact rc1 baseline builds/tests/packages green before contract corrections begin.

## 9. Immediate audit priorities

The highest-value first passes are:

1. public `TerminalSession` construction/lifecycle/ownership surface;
2. result/exception consistency across observation, mutation, leases, and queries;
3. native-mode snapshot exposure vs semantic policy;
4. public protocol methods for duplication/vendor leakage;
5. sample best practices and ownership cleanup;
6. XML documentation for cancellation, disposal, restoration, and security-sensitive output;
7. package metadata and old roadmap authorities.

No conclusion from these priorities should be treated as a request for new protocol support.

## 10. Next step

Perform the T190 public-surface inventory and produce a classified regret-audit record. Only then begin T191 permanent architecture/ownership documentation or any justified D-class correction.
