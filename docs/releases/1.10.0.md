# Icod.Terminal 1.10.0

`Icod.Terminal 1.10.0` adds protocol-neutral semantic capability inspection and explicit bounded verification while preserving the stable `1.0.0` compatibility floor.

Supported target frameworks remain:

```text
net8.0
net9.0
net10.0
```

## Semantic capability planning

Version 1.10 adds a curated public semantic capability vocabulary:

```text
ClipboardRead
ClipboardWrite
CursorStyle
SynchronizedOutput
KeyboardReporting
MouseReporting
FocusReporting
BracketedPaste
RasterGraphics
```

The public planning result keeps support, endpoint availability, evidence kind, and current usability separate through:

```text
TerminalCapabilitySupport
TerminalCapabilityEndpointAvailability
TerminalCapabilityEvidenceKind
TerminalCapabilityStatus
```

Evidence is deliberately dependency- and protocol-neutral. Public callers see `StaticDescription` or `LiveObservation`, not `Icod.TermInfo`, OSC, CSI, DCS, APC, Kitty, Sixel, terminal-brand heuristics, or internal backend identifiers.

## Side-effect-free inspection

The new API:

```csharp
TerminalCapabilityStatus status = session.InspectCapability(
    TerminalCapability.RasterGraphics
);
```

reads the session's current evidence/routing state without emitting terminal bytes or performing a live query.

Support knowledge is independent from endpoint availability. A known capability can remain advertised or verified even when its required endpoint is unavailable in the current session; `IsUsable` then reports false without rewriting truthful support knowledge to `Unsupported`.

## Explicit bounded verification

The new API:

```csharp
TerminalCapabilityStatus status = await session.VerifyCapabilityAsync(
    TerminalCapability.RasterGraphics,
    cancellationToken
);
```

may explicitly strengthen current knowledge only where an already-reviewed bounded probe exists.

The initial live-verification set is:

```text
KeyboardReporting
RasterGraphics
```

Capabilities without a reviewed support probe remain inspection-only. Verification also avoids probe traffic when the endpoint is unavailable or current live evidence is already decisive.

The implementation reuses the existing authoritative input/query coordinator; no second reader, raw-query escape hatch, or hidden background probe was introduced.

## Lifecycle and hardening

The 1.10 qualification suite verifies:

- generation-scoped live evidence expires on session invalidation;
- static description evidence survives generation changes;
- concurrent inspection remains deterministic and side-effect free;
- pre-cancelled verification emits no terminal traffic;
- suspended and closed query ownership are respected;
- unavailable endpoints do not trigger probes;
- repeated verification of decisive evidence does not re-probe;
- negative evidence for one backend does not erase an independent viable semantic alternate;
- fresh NuGet-only consumers restore and run against the packed package on all three supported TFMs.

The capability-planning sample demonstrates semantic decision-making without terminal-brand, protocol-family, backend, or dependency-specific branching.

## Dependency coupling

Active tests, samples, and tools no longer duplicate exact `Icod.TermInfo` or `Icod.Timing` version assumptions. `Icod.Terminal.csproj` remains the package authority for its direct dependency requirements, while successful restore/build is the compatibility witness for the package graph.

Fresh package consumers reference only `Icod.Terminal` directly and allow NuGet to resolve its transitive dependency graph.

This is deliberately loose coupling to the public contracts consumed from `Icod.TermInfo`, rather than a test policy tied to one resolved package version.

## Deliberate exclusions

Version 1.10 does not expose:

- the internal backend registry or routing preferences;
- explicit Kitty/Sixel/backend selection;
- raw evidence-ledger entries;
- arbitrary terminfo capability names;
- `Icod.TermInfo` objects as planning results;
- terminal-brand heuristics;
- hidden/background probing;
- a requirement that every semantic capability have a live probe;
- persistent raster resources or placements.

Persistent raster resource/placement lifecycle remains planned for the 1.11 development track.
